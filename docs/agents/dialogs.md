# Dialog standards

Navigation, button, layout and styling rules every modal dialog follows. For the wiring checklist when adding a dialog, see `recipes/new-dialog.md`.

## Navigation

- **Up/Down**: Navigate between content elements (radio items, checkboxes, input fields).
  - Down from the last content element moves to the first button (OK).
  - Down from last button does nothing (no wrap-around).
  - Up from first content element does nothing (no wrap-around).
  - Up from a button goes back to the last content element.
- **Left/Right**: Navigate between buttons only (OK, Cancel, etc.).
  - Left from first button does nothing.
  - Right from last button does nothing.
  - Does not wrap around.
- **Tab/S-Tab**: Jump between *groups* of controls, not between individual items — a radio
  block, a checkbox block, and the button strip are each one group, and Tab lands on the first
  item of the next group (wrapping around). Every dialog gets this from the `dlg` engine (a group is one Tab segment; `Item.Seg` splits it).
  - **Every text input is its own group.** In a dialog with more than one text input, Tab steps
    from one input to the next before it leaves the block (mass rename Find → Replace, chown
    User → Group, symlink Target → Link path). Use Up/Down to step item-by-item inside a group.
- **Enter**: Activates the focused button or confirms the dialog.
- **Esc**: Cancels/closes the dialog (see Button Shortcuts: OK/Cancel are resolved centrally).

## Button Shortcuts

- Buttons have a highlighted shortcut letter in accent color (magenta by default).
- Shortcuts: `O` for OK, `C` for Cancel, `Y` for Yes, `N` for No.
- Alt+letter fires a mnemonic anywhere, also from inside a text input. A plain letter fires it whenever focus is not in a text input. Dialogs with `Spec.AltOnly` (the job conflict dialog screens, the delete confirmation, the remove empty directories confirm) need Alt always: the conflict dialog reopens on a timer and deletions must not be answered by a stray letter.
- **OK and Cancel are resolved once, centrally.** `ui.input.dialog-ok` and `ui.input.dialog-cancel` are `[dialog.input]` actions dispatched in `App.handleKey` through `dispatchDialogButton` (`internal/app/dialog_buttons.go`), which reads the `buttons` (`dialogButtons{OK, Cancel, Esc}`) of the top-most open dialog's `App.activeDialog` entry (`internal/app/active_dialog.go`). A new dialog adds one case there; its key handler must **not** handle the OK / Cancel chords itself. A nil `OK` or `Cancel` means the dialog has no such button (the chord is swallowed); `Esc` is set only where Esc deliberately differs from Cancel (running command-output dialog keeps the command running).
  - Layered dialogs resolve to their innermost layer: handlers with sub-phases, sub-confirms or a path-completion dropdown expose `OK`/`Cancel` funcs that pick the layer (`FileDialogOK`/`FileDialogCancel`, `TransferDialogCancel`, `jobs.Handler.DialogOK`/`DialogCancel`, the Configuration dialog's Yes/No sub-confirms).
  - Dialogs whose OK / Cancel letters are letter choices (the job blocker's Overwrite / Cancel) return zero for rune events; the non-letter `ui.input.dialog-ok` / `ui.input.dialog-cancel` chords still map. Configuration and meta dialogs return zero for the `F9` chord (edit config).
  - The undo confirmation (`UndoConfirmState`, `UndoConfirmView`, `App.handleUndoConfirmKey`; buttons `UndoYes` / `UndoNo`, No focused first) is a `PrimaryModalUndo` modal opened by `jobs.Handler.undoSelectedJob`; its `dialogButtons` case calls `Handler.ConfirmUndo` for Yes and answers No for Cancel.
  - `Spec.AltOnly` turns the plain-letter stage off: mnemonics need Alt even outside text inputs. Set it on dialogs that can appear without a keypress or confirm a deletion.
  - `Item.MnemonicOutsideInputs` (radio and checkbox) keeps an item's mnemonic undrawn and dead while focus is in a text input, so the input keeps that Alt+letter (Find's advanced options).
  - Every other button or option letter is a `Mnemonic` in the spec (M-y / M-n on delete, M-a Advanced, M-l Calibrate). A handler whose own keys run before the engine (completion, path shortcuts, chords) runs `dlg.HandleMnemonic` first, the engine's Alt+letter stage on its own, so a mnemonic wins over every key of theirs (transfer, flatten, the file dialog family, debounce calibration).
  - **Modal dialogs outrank global keys.** `App.handleKey` gives a modal its keys right after `handleGlobalKeyIntercepts` (terminal panel focus, quit, `jobs.answer-blocker`, `app.show-help`), so a modal mnemonic may reuse a global view key (`messages.open`, `jobs.open`, ...): debounce calibration, compare merge and select group do. Do not avoid global keys in modals.
  - **Inline panes are the exception.** A dialog-like pane inside a view (the jobs-view blocker pane, `handleJobsConflictPaneKey`) gets keys only after its view handler has run `TryDispatchAuxiliaryScreens`, so a global view key there opens that view instead. Its letters must avoid the global view keys, and a modal that asks the same question (the File exists dialog) uses the same letters as the pane, so Skip All is K in both.
- An Alt-letter mnemonic (a checkbox, a radio or a button) **never moves focus out of a focused
  text input**: the user keeps typing after flipping the option or after a button that refused
  (Advanced, a disabled Apply). From a non-input row it moves focus to the activated widget
  (group select, filter, mkdir actions follow this).
- Off a text input a plain letter acts as its Alt+letter mnemonic (`dlg.HandleKey`, `handleRune`),
  including focusing the widget, unless the spec is `AltOnly`. A text input keeps every plain
  letter as text. The focused option also toggles with Space or Enter.

## Rendering / Styling

- All dialogs use `styles.DialogSurface` as the fill color, not `styles.DialogText`.
- A spec with `dlg.Spec.PanelChrome` is drawn in the active file-list panel's surface, frame, title and row text instead (`theme.DialogOnPanelChrome`, applied once in `dlg.Draw`), for content themed for that panel; buttons and inputs keep their dialog styles.
- The border uses `styles.DialogFrame` on the dialog background.
- The title row is built from `styles.DialogTitle` **attributes** (`bold`, etc.) with **glyph foreground** taken from `dialog.frame` and **glyph background** from `dialog.surface` (see `DrawDialogFrame` in `internal/ui/dialog/internal/draw/chrome.go`).
- All content rows use the dialog background as their background color.
- **Do not** add navigation help footers (e.g. `Left/Right  Enter confirm  Esc cancel`) at the bottom of dialogs. Standard dialog navigation and button Alt-shortcuts are enough; the user does not want keyboard cheat-sheet rows in the UI.
- Buttons use the `draw.DrawDialogButton` helper (`internal/ui/dialog/internal/draw/button.go`), which renders start cap + label + end cap. The caps are `[icons.dialog.button]` `start` / `end` (default the powerline half-circles of a pill; spaces included, never trimmed; `Theme.DialogButtonCaps`, which returns `[ ` / ` ]` without Nerd Font icons, as wide as the pill so the icon setting never changes button width; `Theme.DialogButtonCapsStyled` is then false and the cap colors are skipped. `SetButtonCaps` stores caps and that flag together) and count toward the button width. Layout (`dlg.Place`, `ButtonRowXs`, `DialogButtonWidth`) has no theme in hand, so the caps are process-wide: `App.setStyles` calls `dlg.SetButtonCaps` (default theme's caps until then), and drawing reads the same pair. The whole button uses `DialogButtonActive` / `DialogButtonInactive` (and `DialogButtonActiveDestructive` when `DialogButtonSpec.Destructive` is set) **as defined in the theme** (foreground and background; do not substitute `dialog.surface` for button fill); each cap's non-space runes take the state's `dialog.button.<state>.start` / `.end` fg and bg (`Theme.DialogButton*Caps`, each when set) over that style, while cap spaces stay in the button style (`drawCap`), for edge effects such as a raised highlight / shadow.
  - Shortcut letter in `dialog.accent` foreground color (`Theme.DialogAccent`), bold; in `dialog.accent_alt` (`Theme.DialogAccentAlt`, optional, falls back to `dialog.accent`) while the letter needs Alt: the spec is `AltOnly`, or focus is in a text input (`dlg.needsAlt`, the one rule key handling and drawing share; `dlg.Draw` and `dlg.DrawButtonHover` swap the accent via `mnemonicStyles`). Dialogs drawn outside `dlg` with plain letters (the jobs-view blocker pane) keep `dialog.accent`. The focused button's letter instead takes `dialog.button.active.accent` / `active_destructive.accent` (`Theme.DialogButtonActiveAccent` / `DialogButtonActiveDestructiveAccent`), or their `accent_alt` forms when it needs Alt: its face (`button_focus_bg`) may be light where `dialog.accent` is made for the dark surface. `Theme.WithAltMnemonics` is the one swap of all three accents for their Alt forms (`mnemonicStyles`, the theme preview).
- Checkbox and radio rows (and Markers and `CellColumns` lists) use `Theme.DialogOptionMarkerStyles`: the label follows focus only (`dialog.option.active` / `dialog.option.inactive`), and only a checked marker glyph takes `dialog.option.selected`, so the cursor row looks the same checked or not. Plain list rows without a marker glyph use `Theme.DialogOptionRowStyle`, where `dialog.option.selected` / `dialog.option.active.selected` color the whole row. Row background always matches `dialog.surface` — do not set `bg` on option keys.
- Do not use `styles.DialogText` for input row fill; input rows use `theme.Theme.DialogInputPair(focused)` (resolved from `dialog.input.active` / `dialog.input.inactive` and their `.placeholder` entries). Those styles carry both foreground and background for the input row—do not substitute `DialogText` for fill.

### Text overlaid directly on a border (not inside a dialog)

Any label painted on top of a panel/dialog border line (top-row end labels like the Queue
rate-limit indicator or compare/dedup filter indicators, bottom-row selection-size indicators,
etc.) must carry one space of padding on each side so it doesn't run flush into the border
dashes — `──100MB/s─` is a bug, `── 100MB/s ─` is correct. Use `panelSelectionSizePadded` /
`SelectionSizePadded` (`internal/ui/selection_size.go`) to pad the raw text; do not pass an
unpadded string to `drawAuxPanelChrome`'s `endLabel` or similar. Exception:
`drawAuxPanelBottomCenterLabel` (`internal/ui/panel_chrome_draw.go`, bottom-border centered
legends such as the compare and dedup cursor-row icon legends) pads internally, so pass it raw
text, never pre-padded. This has been missed repeatedly (the jobs rate-limit indicator, the
dedup icon legend) — when adding any border-overlaid label, check the rendered row shows
`─ text ─`, and assert the surrounding spaces in its render test.

## Horizontal columns (do not confuse `rect.X+1` and `rect.X+2`)

Use `draw.DialogTextX(rect)`, `draw.DialogOptionX(rect)`, and `draw.DialogContentWidth(rect)` in `internal/ui/dialog/internal/draw/geom.go` instead of re-deriving offsets.

- `rect.X` — left border (`│`); `rect.X+1` — inner margin (blank dialog surface).
- **Labels, hints, and input rows** — `DialogTextX(rect)` (`rect.X+2`): first content glyph one space inside the border (e.g. `Destination:`, `/path`, command field).
- **Checkbox / radio rows** — pass `DialogOptionX(rect)` (`rect.X+1`) to `draw.DrawDialogCheckbox` / `draw.DrawDialogRadio` only. Markers are ` [ ] ` / ` ( ) ` (`draw.CheckboxMarker` / `draw.RadioMarker`, also used by `dlg.MarkerWidth` and `Markers` lists) with a **leading space** that fills the margin cell; the visible `[` or `(` must land on `DialogTextX`, not one column to the right.
- **Common bug:** `DrawDialogRadio(screen, rect.X+2, …)` paints an extra blank column before `( )`, so options look indented relative to labels (seen on Run-for-each pool rows). Copy/move checkboxes (`TransferView`) and Find checkboxes use `rect.X+1` — match that, not `rect.X+2`.
- **Inner width** — `DialogContentWidth(rect)` (`rect.Width-4`) for full-width text and inputs between margins.

## Mouse

`dlg.Click(spec, w, h, &focus, x, y, double)` and `dlg.Wheel(spec, w, h, &focus, x, y, delta)` (`internal/ui/dialog/dlg/mouse.go`) are the engine's mouse entries. They place the spec like `Draw`, move focus to the widget under the cell and return the `dlg.Event` the matching key would produce, so the dialog applies a click with the same code as a key:

| Press | Focus | Event |
|---|---|---|
| button | the button | its activation (`dlg.OK` / `dlg.Cancel` run the `activeDialog` entry's buttons when the dialog sets them) |
| radio / checkbox | the option | its activation, `Event.Enter` unset: a click toggles like Space |
| input | the input | `EventCaret` with `Index` = the rune under the pointer (past the `LeadingIcon` and its space, from the item's `Scroll`, wide runes two cells, clamped to the text end) |
| list row | the list, or a driven list's input | `EventListMove` onto the row; a double click (`config.MouseDoubleClickMS`) on the cursor row is the activation Enter produces there (`Event.Enter` set) |
| wheel over a list | the list, or its driving input | `EventListMove` by `config.MouseWheelRows`, clamped |

**Hover.** `dlg.HoveredListRow(spec, w, h, focus, x, y)` returns the screen rect of the list row under the pointer and `dlg.DrawListRowHover` repaints its cells on the `jobs.row.hover` background, keeping text and foreground; the list cursor and focus never follow the pointer. `ScrollOnly` lists, `Header` rows, rows past the last and the cursor row of a focused list get no highlight. `App.render` stores it in `Model.DialogListHover` (`dialogHovers`, zero width for none; hidden after a key press like every hover, `architecture.md`) and `ui.Render` paints it after `drawModalOverlays`. `dlg.HoveredButton(spec, w, h, x, y)` returns the strip button under the pointer as a `dlg.ButtonHover` (placed rect, label, mnemonic, destructive), and `dlg.DrawButtonHover` repaints it in the focused button style (`DialogButtonActive` / `DialogButtonActiveDestructive`) without touching focus. `App.render` stores it in `Model.DialogButtonHover` (`refreshPointerHovers`, from the top-most `activeDialog` spec and the last pointer cell) and `ui.Render` paints it after `drawModalOverlays`, so the highlight is recomputed from the dialog as drawn on every frame.

Labels, separators, spacers (reserved regions: the theme preview pane), bars, disabled widgets, `ScrollOnly` lists, `Header` rows and rows past the last row are misses for `Click` (the wheel still scrolls a `ScrollOnly` list, leaving focus where it is): no event, focus unchanged, and `App.handleDialogMouse` swallows the press.

Each dialog's key handler is `dlg.HandleKey` followed by one event function (`applySortDialogEvent`, `find.Handler.ApplyDialogEvent`, `ApplyTransferEvent`, `ApplyPatternDialogEvent` for the Filter / Group Select twins, `ApplyFileDialogEvent` for the file dialog family and its picker screens...), and the mouse calls that same function. An event function of a dialog with inputs handles `EventCaret` first (set the field's cursor: `FileDialogField.SetCursor` commits a pending prefill, path fields re-sync completion through `setPathFieldCursor`), because an event carrying an input's ID otherwise means Enter in it. Rules that tell Enter from Space read `Event.Enter`, never the raw key. **Sub-screens.** A dialog whose sub-screens take the place of its main screen (the file dialog's pickers, the conflict rules, the Configuration Yes/No confirms) decides which is on top in one place: a `Screen` method on its state returning a `dialog.DialogScreen{Spec, Focus}`, the spec of the screen on top and a pointer to the focus field it is driven with (`FileDialogState.Screen`, `ConflictDialogState.Screen`, `ConfigDialogState.Screen`). The renderer, the key handler and `activeDialog` all read it; nothing else switches on the phase to pick a spec or a focus. **`App.activeDialog` is the table** (`internal/app/active_dialog.go`), read by the button chords, the mouse and the dialog invariants: one case per dlg dialog, returning the spec as drawn (built on demand, `ok` false when it does not fit), a pointer to the focus field its key handler reads (a scratch focus for handlers that keep their own: message, pin), its event function and its OK / Cancel buttons. The spec must come from the same builder and inputs as the renderer and the key handler (`PreviewSettingsDialogView` takes the marker width, `ui.DedupReturnSpec` is shared with `render.go`, handler specs such as `FileDialogSpec`, `PathPickerView`, `TransferDialogSpec`, `BlockerDialogSpec` and `find.Handler.DialogSpec` are exported for it and used by the key handler too), or clicks land on the wrong widget.

## Code Structure

- Button rendering: `draw.DrawDialogButton` (`internal/ui/dialog/internal/draw/button.go`); centered rows via `DrawDialogButtonRowCentered`.
- Focus management lives with the dialog's handler: `internal/apphandler/dialog` for most dialogs, `internal/app` for the ones that stay app-side (see `architecture.md`, Package layout). `internal/app/input.go` owns top-level key dispatch.
- File dialogs (`FileDialogState`) all run on `FileDialogView`; `Focus` is a `dlg.ID` (`FileFieldID(i)` for the inputs, a checkbox / radio ID, `dlg.OK`, `dlg.Cancel`). The run-for-each history picker and the mass rename pattern pickers are screens of the same state with their own `Focus`.

## Shared dialog sizes

Find (`FindDialogView`) and the file picker (`PathPickerPurposeNavigateFile`: other copies, the differences report) share one frame size. **A size change to either dialog must be mirrored in the other.**

- Width: both use `findDialogPreferredWidth`, so changing the const moves both.
- Height: the file picker's list is `findListHeight` plus `pathPickerFindExtraRows`, the rows Find spends above its list that the picker lacks. Changing `findListHeight` moves both; adding or removing a permanent row in either dialog means updating `pathPickerFindExtraRows`.
- `TestPathPickerFileMatchesFindSize` compares the two frames on several layouts and fails when they drift. Do not change its expectations to get past a mismatch: fix the sizing.
- Accepted differences: Find's optional `FindSelections` row makes it one row taller than the picker, and below 58 terminal columns Find does not draw while the picker still does (`MinWidth` 54 against 36).
- The other path picker purposes keep the standard picker size (78 columns, `pickerListHeight`) and are not part of this pair.

## Declarative dialogs (`dlg` engine)

- `dlg.Place` is the only geometry pass. `Draw`, `HitTest`, `Click` and `Wheel` read its `Placement`; nothing re-derives rects. Button x positions come from `draw.ButtonRowXs`, shared with `DrawDialogButtonRowCentered`. The button strip is drawn directly under a separator, with no blank row between them.
- **Sizing**: `Spec.Width` is the preferred width and `Place` widens it to fit the button strip between the borders (`draw.ButtonRowWidth`). By default the dialog is clamped to the screen (`draw.ClampCenteredDialogRect`) and `Place` refuses when it cannot reach `MinWidth` / `MinHeight`. `Spec.Unclamped` sizes like `draw.CenteredDialogRect` instead and always draws: width is `min(Width, screen-4)`, widened to `min(MinWidth, screen-2)` when below `MinWidth`; the height only shrinks to the screen (`Spec.Margin`: to the screen less a row above and below, and the dialog does not draw when its lists cannot keep their `MinHeight` in that). Height always fits the rows (`MinHeight` raises it); never pick an oversized height. `Spec.MustFit` makes a dialog not draw where any of its content would be cut off (sort, compare filter, Configuration) rather than a `MinHeight` that restates its height. `Spec.MaxHeight` is the tallest the dialog wants to be (the delete and copy / move dialogs' 80% of the screen, `listDialogMaxHeight`; help, command output and mass rename): its lists shrink to fit it, and it gives way to rows that cannot shrink (fixed content, lists at their `MinHeight`), so it never cuts content off. List heights are never computed by counting the dialog's other rows: a list's `Height` is the most rows it wants and the engine fits it (Lists, below).
- **Labels**: an item of `Kind: dlg.KindLabel` is a static text row in the dialog text style (`DialogText` on `DialogSurface`), starting at `DialogTextX` and truncated with an ellipsis to the content width. An empty `Label` is a blank spacer row. A label cell of a row may carry a `Mnemonic`: Alt+letter then steps the row's radios to the one after the selected one (wrapping, skipping disabled radios; the Preview settings capability rows). Labels have no ID or state, are skipped by every focus move, and are not hit-test or click targets. A group made only of labels is not a Tab segment. Labels may sit between items of a column.
- **Label variants** (`KindLabel` only): `Indent` (extra cells before the text), `Fit` (`FitRight` ellipsis at the end, `FitMiddle`, `FitPath` = `primitive.FitPathForWidth`), `Prefix` (fixed text before `Label`, only `Label` is shortened), `Style` (`TextNormal`, `TextError` = `DialogText` with the input error foreground, `TextMessageError` = the theme's `MessageError` style on the dialog surface) and `Center`. The View never measures the screen: the engine fits labels into the width `Place` gives them.
- **Separators** (`KindSeparator`): a full-width rule (border to border) drawn with `draw.DrawDialogHSeparator` in the frame's border style; a non-empty `Label` is centered in it, padded with one space each side (`draw.DrawDialogHSeparatorWithCenteredLabel`, `DialogTitle` attributes on the frame foreground). Not focusable, not a hit target, no ID needed; it takes one row and always spans the dialog whatever column it sits in. Put it in a group of its own or at the end of the group it closes; a group of only labels and separators is not a Tab segment. The button strip still draws its own separator, so do not add one right above it.
- **Inputs** (`KindInput`): a single-line text input across its column's text width (in a one-column group that is `DialogTextX` / `DialogContentWidth`; in a multi-column group it stops one cell before the next column, like a list). Item fields mirror `draw.ScrollingInputState` (`Value`, `Cursor`, `Scroll`, `CompletionSuffix`, `LeadingIcon`) plus `Invalid` (error styling), `Placeholder` (the value is a suggested default, drawn in the placeholder style: prefill pending), and `Simple` (`draw.DrawSimpleDialogInput`: no scrolling, ghost text or icon). The engine never edits text; `Value` / `Cursor` / `Scroll` stay in the dialog's state (`FileDialogField`, `lineedit`, `scrollquery`...), and the editor keeps `Scroll` for `dlg.InputTextWidth(screenW, screenH, spec, id)`, the placed width less the leading icon's cells (never a width re-derived from the dialog's) and the View copies them into the item (`fileFieldInput` does it for a `FileDialogField`, including ghost completion and prefill). A masked input is the View passing `*` runes as `Value`.
  - **Key contract while an input is focused** (`HandleKey` doc comment is the reference): Up/Down and Tab/S-Tab move focus, and every input is its own Tab segment even when inputs are adjacent; Enter returns `Event{ID: input}`, which the caller treats as submit / OK; Alt+mnemonic of a checkbox or radio returns that widget's event but leaves focus in the input (a button mnemonic too); Space, plain letters (a text input keeps them, plain mnemonics included), Left/Right, Home/End, Backspace, Delete and every other key return `(Event{}, false)` so the caller feeds them to its existing text-editing code. The usual caller order is: completion dropdown / path-picker shortcuts, then `dlg.HandleKey`, then the text editor when the engine declined and the input is focused.
  - **Mouse**: `Click` on an input focuses it and returns an `EventCaret` whose `Index` is the rune under the pointer (see Mouse).
  - **Overlay escape hatch**: `dlg.Draw` (like `dlg.Place`) returns the placement it drew, and `Placement.Item(id)` the rect of any widget. A dialog that needs an overlay anchored to an input (the path completion dropdown, a validation hint) paints it itself right after `dlg.Draw`, using that rect from the returned placement (`DrawFlattenDialog`); it does not place the spec a second time. This is the only allowed way to draw outside the spec; the overlay must not take focus or hits from the engine.
  - **Tooltips**: `Item.Tooltip` on any focusable widget is an explanation the engine draws, last, while that widget holds focus: a box in `[tooltip]` styles (`draw.TooltipLines` wraps it to at most `draw.TooltipMaxWidth` cells, a newline in the text always starting a new line: write one sentence or syntax line per line; `draw.PaintTooltip` paints it with the `[icons.dialog] info` icon at the left of its first line, the text in a column after it). Its left edge is the focused widget's, shifted left only as far as the box needs to fit the frame. It opens on the row below the widget, or ends on the row above it when there is no room below, always inside the frame and above the content bottom (a box that fits nowhere is not drawn), so partial repaints need no extra area tracking. `dlg.PaintTooltipFor` is that placement for a widget rect and text, which the theme picker's preview also calls. `Placement.Tooltip` is its rect; `Placement.EachListRow` skips rows whose first cell it covers, so row-icon overlays never paint over it. It never takes focus or hits. `[ui] tooltips = false` turns them all off (`theme.Theme.HideTooltips`, stamped from the config by `App.setStyles` like `UseNerdfontIcons`). Use it for syntax and semantics that would crowd the dialog as inline text (find's advanced inputs, `findAdvTooltips`).
- **Lists** (`KindList`): a scrollable list of plain-data rows (`Item.Rows`, each a `dlg.ListRow{Text, Match, Marked}`). The rows, `Cursor` (the cursor row, shared with an input's caret field) and `Offset` (first visible row) stay in the dialog's state like an input's text; the View copies them into the item, and the caller stores the `Cursor` / `Offset` of every `dlg.EventListMove` back. `Height` is the most rows the list wants (one per row, a cap such as `pickerListHeight` or `findListHeight`, or the whole screen for a list that fills its dialog) and `MinHeight` the fewest it keeps (`Place` fails rather than go below it); `Place` shortens lists to fit `Spec.MaxHeight` and the screen. `dlg.FitSpec(screenW, screenH, spec)` returns the spec with those heights resolved, as `Place` lays it out: Views return the fitted spec, so `HandleKey` pages and clamps by the drawn height, and callers that keep a list's scroll read its height from the spec (`Spec.Item(id).Height`; `HistoryDialogListRows`, `PinDialogListRows`, `PathPickerListRows`, `SFTPConnectListRows`, `FindDialogMetrics`, `ComputeHelpDialogListMetrics`, `CommandOutputDialogListH`). A list whose rows depend on its height (windowed rows) or its placed width (pre-fitted columns) is built through `dialog.fillList`: the View describes the spec with a placeholder list, `fillList` fits it and builds the list for the height and width it got. Options: `Wrap` (Up/Down/PgUp/PgDn wrap around the ends), `CenterScroll` (the cursor row stays centered, `geom.ScrollOffset`; otherwise the viewport is sticky and moves only as far as needed, `geom.ScrollOffsetEdge`), `PageStep` (PgUp/PgDn rows; default `Height-1`, a full `Height` on a `ScrollOnly` list), `Markers` (radio glyph per row, lit by `ListRow.Marked`; the list is placed at the column's option x so the glyph's leading space fills the margin cell and `(` lands on the text x, like a radio row; every row an option row with its `Match` highlights, rows past the data left as bare surface; without it rows are plain dialog text, a `Marked` row is drawn in the selected option style (find's marked results), the focused cursor row is an active option row and unused rows are painted in the dialog text style), `Fit` (`FitRight`, `FitMiddle`, `FitPath` for overlong rows, `FitNone` for pre-fitted rows; `ListRow.Match` fuzzy-highlight ranges are mapped onto the shortened text), `Scrollbar` (`draw.DrawDialogListScrollbar` on the dialog's right border when the rows overflow `Height`, in `Spec.ScrollbarStyle`) and `Driven` (below). `Item.ViewOffset()` (`dlg.ListViewOffset` for callers that hold only the row count, as `EnsurePickerScroll` does) is the one viewport function behind `Place`, `Draw`, `Click`, `Wheel` and every event, so the stored `Offset` can go stale without hiding the cursor. Long lists are windowed: `Item.RowCount` is the row count and `Rows` holds only rows `[RowsFrom, RowsFrom+len(Rows))`, at least the `dlg.ListWindow` range, so per-row work (paths, marks, column formatting) runs for visible rows only (Find, History, path picker). Row features for path lists: `ListRow.Icon` (drawn before the text plus one space, shifts nothing else: `Match` stays keyed to `Text`; `Item.IconOptionFG` paints it in the option-row foreground instead of the row style), `ListRow.Missing` (invalid row style unless under the cursor, adds the missing mark) and `ListRow.Marks` (`dlg.RowMarks`: pinned / job / missing / range-anchor icons, drawn by `dlg.DrawRowMarksSuffix`; `dialog.RowMarks` is an alias). Marks sit at the row's right edge by default (the text is fitted to what is left), after the text with `Item.MarksAfterText`, and `Item.MarksWidth` reserves one uniform column on every row (unused rows keep it painted). `dlg.FitNone` draws rows the caller already fitted (column grids): `ListRow.Match` are offsets into the displayed text. `ListRow.Spans` are pre-styled rune ranges of the text (ANSI colors, a key column, a diff) under the `Match` highlights, for `FitNone` / `FitRight` rows; the cursor row drops them. A `Header` row (`dialog.help.section` style) never holds the cursor: motion steps over it, a click on it is a miss, and the viewport reveals the header rows right above the cursor row while the cursor still fits. A `ScrollOnly` list is a view without a cursor: never focused, `Offset` its only state (`dlg.ScrollViewOffset` keeps the last page full); PgUp / PgDn scroll it from any widget that does not use them, Up / Down when focus has nowhere to move, Home / End from a button or option, and the wheel over it, each as an `EventListMove` carrying the new `Offset`; a spec has at most one.
- **Checkbox grids** (`KindList` with `Markers` and `CellColumns`): each `ListRow.Cells` entry is a `dlg.ListCell{Text, Match, Check}` with a tri-state `dlg.CheckState`, in equal-width columns. Rows stay the unit of `Cursor`, `Offset`, `Height` and the scrollbar; `Item.Col` is the cursor's cell, carried in `Event.Col`. Left/Right move between a row's cells, Up/Down keep the column (clamped on a short last row) and leave the list at its first and last rows, Enter and Space activate, and a click activates the cell under it directly (`Event.Enter` unset). `HoveredListRow` returns that cell. See `IndexTagsDialogView`.
  - **Key contract while a list is focused** (`HandleKey` doc comment is the reference): Up/Down move the cursor one row, PgUp/PgDn by `PageStep`, Home/End (with or without Ctrl) jump to the first / last row; the key is consumed at the ends too (Up on the first row never leaves the list) unless `Wrap` is set. Each move returns `Event{ID: list, Kind: dlg.EventListMove, Index: cursor, Offset: viewport}`; the caller applies it (and does any side effect such as the theme preview). Enter and Space return `Event{ID: list, Index: cursor}` (`dlg.EventActivate`). Tab/S-Tab leave the list: every list is a Tab segment of its own. Left/Right do nothing. A plain letter acts as its mnemonic (unless `Spec.AltOnly`) and is `(Event{}, false)` when it has none. Alt+mnemonics behave as everywhere. An empty list is never a focus stop.
  - **Filter drives list**: an input with `Item.Drives` naming a list steers it while it is focused and the list has rows: Up/Down/PgUp/PgDn and C-Home/C-End return the list's `EventListMove` and focus stays in the input (plain Home/End stay text editing keys). With an empty list those keys move focus like in any input. The list is marked `Driven`: it is not a focus stop or Tab segment itself, its cursor row is lit while the driving input is focused, and a click on a row focuses the driving input. Enter on the input still returns `Event{ID: input}`; the caller reads the cursor from its state. The text editing stays the caller's (`editSFTPConnectDialog`); after a filter change the caller resets the cursor and re-derives `Offset` (`EnsureSFTPConnectListScroll`).
  - **Mouse**: `Click` on a list row returns the `EventListMove` onto it (focus: the list or, for a driven list, its driving input), a double click on the cursor row its Enter activation, and `Wheel` a clamped move. Rows past the last row are not hits (`PlacedItem.Offset` / `Rows` describe the visible window).
  - Motion is not reimplemented: `listKey` uses `filterlist.NavKey` / `filterlist.ClampedDelta` and `geom` scroll offsets, so the keyboard and the wheel share one implementation.
- **Rows** (`KindRow`): `Item.Cells` are laid out left to right on one dialog row, each cell a radio, checkbox, label, input or spacer with its own ID, placed rect, focus stop and hit rect (rows hold no lists, separators or further rows). A cell's box starts where the previous box plus that cell's `Gap` (blank cells after it) ends. `Width` > 0 is the box width in cells, `Width` 0 is the content (marker plus label of a radio / checkbox, one cell plus `Indent` plus text for a label), and `Grow` (an input without `Width` grows too) shares the spare width equally. Radios and checkboxes start in the box's first cell, labels and inputs one cell in (the dialog text column), so a fixed-width label box followed by radios lines the radios up; `Right` right-aligns a label's text in its box (the live preview on the Pattern row is a growing right-aligned label). A row ends one cell before the right border. A row too wide for it first narrows its gaps (down to one cell each; the find options row at 80 columns), then a box that crosses the end is clipped (a radio's label is shortened) and one that starts past it is not drawn (empty rect). `Spec.MarkerWidth` is the width of a marker for content boxes (0 = the ASCII 5; `dlg.MarkerWidth(styles)` gives the theme's, for dialogs whose rows should follow narrower icons). Per-column x offsets of a checkbox grid come from fixed `Width`s derived from the widest label (`patternSpec`), or from `Group.ColWidths` when the cells are stacked columns instead of rows.
  - **Focus in rows**: Left/Right move to the previous / next focusable cell of the row (disabled cells and labels are skipped, the key is consumed at the ends) and never leave a focused input, which hands them to the caller's text editing. Up/Down go to the cell drawn nearest (see the navigation rules below), so rows whose cells share widths (`massRenameColumnWidths`) keep the column, and a greyed cell is passed for the nearest focusable one. A row counts as one item of its column.
  - **Tab segments**: a group is one Tab segment; `Item.Seg` splits it by value (items of a group sharing a `Seg` are one segment, whatever the layout order, so a grid of radio + checkbox rows can Tab between the radios and the checkboxes, and capability rows can be one stop each). A segment starts at its first item in focus order. Inputs and lists stay segments of their own. A row with `Item.TabToSelected` makes Tab and S-Tab land on its selected cell (`On`) instead of the segment's first item (the mass rename mode radios).
- **Bars** (`KindBar`): a full-width progress meter: `Item.Frac` (0..1, a started bar shows at least one cell, `dlg.BarFilledCols`) fills the cell backgrounds `dialog.progress.fill` / `track` and `Label` is overlaid, fitted like a `FitPath` label. Static, not focusable, not a hit target, not allowed in rows. The live content stays in the caller's state (`DedupProgressView` rebuilds the spec on every poll).
- **Button separator label** (`Spec.ButtonsLabel`): text centered in the separator above the buttons, padded by the engine, in the selection-size status style (find's marked-selection size; callers pass it unpadded).
- **Button rows** (`Button.NewRow`): a button starts a new centered strip row. The strip is still one Tab stop; Left/Right walk the buttons in reading order across rows, Up/Down move to the button drawn nearest in the adjacent row like any other widget (Up from the first row leaves the strip), and the separator, every row and the frame always stay inside the dialog when it is clamped. `Placement.ButtonY` is the first row.
- **Disabled** (`Item.Disabled`, radios and checkboxes): drawn with the disabled style (`DialogOptionDisabledStyle`), not focusable, not a mnemonic target, not a hit target. `Item.Inert` draws the same style but stays focusable, a mnemonic target and a hit target; the caller ignores the activation. A focus that points at a disabled item falls back to the first focusable item.
- **Clipping**: when the frame is shorter than the content, lists then spacers shrink (to their `MinHeight`, one row by default) before anything is cut: each row is taken from the columns that make their group as tall as it is, a list before a spacer, so a list and the spacer beside it (the theme dialog's list and preview pane) shrink together. The button separator and strip always stay inside the frame (`Placement.ContentBottom` is the first row content is not drawn on), and content that still does not fit is cut off above the separator. Overlays painted after `dlg.Draw` skip items at or below `ContentBottom`. `Place` fails (nothing is drawn) only below `MinWidth` / `MinHeight`, when a list held at its `MinHeight` keeps the dialog from fitting, or on a `MustFit` spec whenever content would be cut.
- **Columns and the reserved region**: `Group.ColWidths` gives the widths of every column but the last (the last takes the rest); without it columns share the width equally. A `KindSpacer` item reserves `Height` rows of its column for the caller to paint after `dlg.Draw`; it is never focusable or a hit target, and `Placement.Item(id).Rect` is the whole column cell (the theme picker paints its preview pane, vertical rule and frame tees there; the dedup confirmation paints row icons into the cells a label's `Indent` left free). The overlay must stay inside the rect and must not take focus or hits. A scrolling body is a list, not a reserved region: styled text goes in `ListRow.Spans`, section titles in `Header` rows, a view without a cursor is `ScrollOnly`, and per-type devicons are painted after `dlg.Draw` over the cells a row's icon pad keeps free (`Placement.EachListRow`).
- Navigation rules are implemented generically by the engine, so a spec-based dialog gets them without per-dialog code. Focus order is group by group, column-major inside a group, then the buttons; separators and labels are skipped. Up/Down move by where the widgets are drawn (`spatialTarget`, `internal/ui/dialog/dlg/spatial.go`): to the nearest row of focusable widgets below / above, buttons included, and in it to the widget nearest the focused one's columns (an overlapping one first, so a column or a grid column of cells is kept; the leftmost when several overlap). An item of a group column spans its whole column for this, so a narrow radio still owns its column; row cells and buttons span their drawn rect. The columns of a group are lanes Up/Down never cross: leaving a column at its end goes on past the group (Down from the bottom of the sort dialog's meta column reaches the checkboxes, not the mode column). Where nothing is above / below, a `ScrollOnly` list scrolls instead, else focus stays. Left/Right move to the same row of the adjacent column (staying put when there is no focusable item there) and along the button strip. Tab/S-Tab jump between groups and the button strip with wrap (each text input is a group of its own, splitting the group it sits in); in a dialog that is only a button strip they land on the first button. Space and Enter activate the focused widget (buttons included); Alt+mnemonic activates and focuses (except from a text input, which keeps focus); off a text input a plain mnemonic letter activates and focuses like Alt+letter, unless `Spec.AltOnly`.
- The standard strip is `dlg.OKCancelButtons()` (or `dlg.OKButton` / `dlg.CancelButton` next to other buttons). Numbered widget families (radios per option, inputs per field) name their IDs with `dlg.IndexedID(prefix, i)` and parse them back with `dlg.IDIndex`.
- `HandleKey` returns an `Event`; the caller applies it to its state. OK / Cancel / Esc chords are not handled by the engine (see Button Shortcuts). Buttons that are not OK / Cancel (Yes / No, Stay / Quit Anyway, Accept / Save / Reject, Replace / Merge ...) get their own IDs; the caller acts on them, and the `activeDialog` case maps the central OK / Cancel chords onto the right ones.
- The frame, option markers, separator and buttons are drawn with the same `draw.*` helpers as the other dialogs, so styling rules above apply unchanged. Labels in columns after the first are truncated to their column.

## Input Area Rendering / Styling

All dialogs with labeled content blocks (text inputs, radio groups, checkbox groups under a section label) must follow these rules:

### Layout

- The label and the content below it must be on separate rows.
- **The content row sits directly beneath its label row — no blank row between them** (text input, first radio/checkbox option, preview value, etc.). This is the compact layout, and it is the convention everywhere; a dialog that spaces a label away from the thing it labels is a bug, not a style choice.
- Do not place the label and its content on the same line, even with visual separators.
- Section labels followed by radio or checkbox options use the same pattern as text fields: **label row → option rows** (e.g. Run-for-each **Worker pool (optional):** then pool radios). Standalone option rows without a section label (e.g. mkdir post-action radios directly under a separator) do not need an extra label row.
- Blank rows still do section work: one blank row above the first button row (see below), and a blank row between a section's last content row and the next section's label where no separator already does that job. What went away is only the gap between a label and its own content.
- Guard: `TestDialogLabelsAreFollowedByContentRow` (`internal/ui/dialog/dialog_label_spacing_test.go`) renders dialogs and asserts the row under each label is the content. Add a case for every new labelled row.

- Elements should be spaced and aligned following these examples:

NO:

┌─ Copy ──────────────────────────┐
│Destination:/home/user/projects  │
│[x] Preserve permissions         │
│[x] Preserve timestamps          │
│  <area for buttons>             │
└─────────────────────────────────┘

YES:

┌────────────── Copy ──────────────┐
│ Destination:                     │
│ /home/user/projects              │
├──────────────────────────────────┤
│ [x] Preserve permissions         │
│ [x] Preserve timestamps          │
├──────────────────────────────────┤
│       <area for buttons>         │
└──────────────────────────────────┘

NO:

┌──────────────────────────────────────────────────────────┐
│  [x] Focus after rename                          [x] Fail│
└──────────────────────────────────────────────────────────┘

YES:

┌──────────────────────────────────────────────────────────┐
│ [x] Focus after rename                          [x] Fail │
└──────────────────────────────────────────────────────────┘

There should be ONE space after (and before) border.


Pay attention to following details:
- Title Copy is centered. Surrounded with empty spaces.
- ONE space margin at the left (`rect.X+1`); first label/input glyph at `DialogTextX` (`rect.X+2`). Checkbox/radio helpers at `DialogOptionX` (`rect.X+1`) — see **Horizontal columns** above. Dialog is scaled so that there is ONE space margin at the right side.
- Input text area is in it's own line. It should cover the all avaialable space in the dialog (respecting 1 space margin).
- Buttons should be visually centered.
- Separation lines between sections.
- **Exactly one empty row above the first button row** (not zero, not two or more). That blank row is dialog surface only—do not paint text on it. Content (or a section separator + prompt) ends on the row immediately above that blank row.

#### Button row placement (read this before sizing `height`)

- **Flow `y` downward** while drawing content, then `y++` once for the mandatory blank row above buttons, then paint button row(s). Single-button dialogs: `buttonY = rect.Y + rect.Height - 2`, blank row at `buttonY - 1`, separator/content ending on `buttonY - 2` when a separator precedes the button block. Dialogs built on the `dlg` engine instead put the button strip directly under the separator; the separator is the divider, so they have no blank row.
- **Size `height` to fit** — do not pick an oversized fixed `height` and anchor buttons with `rect.Y + rect.Height - N`; that leaves extra blank rows beyond the single required one.
- **Two button rows:** second row at `rect.Y + rect.Height - 2`, first at `rect.Y + rect.Height - 3`, blank row at `rect.Y + rect.Height - 4`, content ending above that (separator/prompt on preceding rows).
- **Precompute row count** before `CenteredDialogRect`, or advance `y` while drawing (include `y++` for the button blank row) and set `height = y - rect.Y + 2` (last painted row + one inner bottom margin + bottom border).
- **Common bugs:** (1) `height := 17` with buttons at `height - 4` / `height - 3` plus a help footer — three or more blank rows above buttons. (2) Drawing buttons on the row immediately after the prompt/separator — zero blank rows above buttons.

### Styling

- For any dialog text input row, use `theme.Theme.DialogInputPair(focused)` (`internal/theme/theme.go`). It returns:
  - **base**: row fill + normal (committed) text
  - **placeholder**: dimmed suggested/default glyphs
- Do not override the input row background with `DialogSurface` or chrome-derived `.Background(...)`; the theme’s input row background is intentional.
- Labels stay on the dialog surface (`DialogText` on `DialogSurface` background).
- When adding or correcting alignment avoid using empty spaces to do it. Like string " value" or " value ". Instead adjust rendering position or formatting. Spaces are good only when the background matters.

### Suggested default / prefill (`FileDialogField`)

Logic lives in `internal/ui/dialog/dialog_field.go`. When opening a dialog with a suggested value, set `Value` and `Prefill` to the suggestion and set `PrefillPending` when the suggestion is non-empty.

The suggestion and ghost completion text paint in `dialog.input.*.placeholder`; the caret always reverses the input's own style (`dialog.input.active`, or `.error` when invalid), never the placeholder, because a reversed placeholder blends into `dialog.surface`.

- **First printable (`InsertRune`)**: clear `Value`, reset cursor, clear `PrefillPending`, then insert the rune (replace-from-scratch on top of the suggestion).
- **Backspace, Delete, cursor moves (`MoveCursor` / Home / End via handlers)** call `commitPrefill()` first: drop `PrefillPending` but **keep** `Value`, then apply the usual edit/move.
- **`Clear`** (file dialog `ui.input.kill-line`): empty `Value`, cursor `0`, `PrefillPending` false.
- **`RestorePrefill`** (`ui.input.restore-default`, configurable under `[dialog.input]`): re-arm the suggested default after editing or clearing — `Value` becomes `Prefill`, cursor moves to the end, `PrefillPending` is set to true. No-op when `Prefill` is empty.
- **OK while still pending**: use current `Value` (still the full suggestion)—no extra commit step required.

### Helpers

- Use `fileFieldInput` (a `dlg.KindInput` item) for `FileDialogField`-based inputs in spec dialogs, `drawInputField` in `internal/ui/dialog/file_dialog_render.go` for the inline query bars that still paint an input themselves (both support placeholder-pending rendering).
- Use `draw.DrawSimpleDialogInput` in `internal/ui/dialog/internal/draw/chrome.go` for simple string inputs (no placeholder-pending concept).

## Twin dialogs: Filter and Select group

Filter (`panel.filter-dialog`) and Select/Unselect group are twins: same mode radios, file-type checkboxes, Files/Dirs only, Case sensitive, meta row, live preview, reserved hint row, width and grid navigation. Both build their spec with `patternSpec` (`pattern_dialog_view.go`) and route keys through `dialogctrl.HandlePatternDialogKey` (`internal/apphandler/dialog/pattern_key.go`: engine first, Enter on a checkbox confirms, declined keys edit the pattern). Both open with a ghost `*.<ext>` pattern from the cursor row (`dialog.GhostExtPattern`, drawn as a placeholder while `PrefillPending`; `PatternKeys.PrefillPending` makes the first plain rune replace it and other edits commit it). **A change to one that is not in that shared code (options, matching, preview, hint/error behaviour) should generally be mirrored to the other in the same change.** When a difference is intentional, record it in `docs/agents/panels.md`.

- **File pairs**: `internal/ui/dialog/filter_hint.go` ↔ `groupselect_hint.go`, `filter_dialog_view.go` ↔ `groupselect_dialog_view.go` (`FilterDialogView` ↔ `GroupSelectView`, each state's `Apply`), `filter_dialog_render.go` ↔ `groupselect_dialog_render.go`, `internal/apphandler/dialog/filter.go` ↔ group-select handlers in `internal/app/dialog_settings.go` (find context: `internal/apphandler/find/group_select.go`, `group_count.go`). User docs for both: `docs/panel-filter.md`.
- **Shared code (extend, don't duplicate)**: `pattern_dialog_view.go` builds the whole spec for both (`patternSpec`: radio + type-checkbox rows, Pattern row with preview, input, hint row, option rows; `patternToggles.apply`, the one place radio / checkbox activations change state; the `Pattern*` widget IDs; `patternPreviewText`, `patternHintText`, `patternInvalid`), `dialog.PatternDialogWidth` / `patternDialogFrameWidth`, `dialog.FilterTypesRegexp` (takes the dirs-only flag), `dialog.PatternTypesDisabled` (type checkboxes are `Disabled` items while Directories only is selected: not focusable, mnemonics inert), `FilterTypeLabels`/`FilterTypeMnemonics`, `panel.FilterSpec.MatchFunc`. Both handlers feed keys to `dlg.HandleKey` first; the pattern input's editor (`scrollquery`) gets what the engine declines and never sees an Alt+letter that is a mnemonic of either dialog (`PatternAltIsMnemonic`).
- **Intentional differences**: Filter has Invert and also targets Compare/dedup rows; Select group has Match full path (find context, M-h) and its preview counts only selection-state flips. Select group also has an `output` context (command-output dialog detected paths, Match full path shown like find, no meta columns) and a `dedup` context (Find duplicates marks, see [views.md](views.md) "Marking"); Filter has no equivalent of either.
- **Mnemonics**: one letter per option across both dialogs, defined once as the `PatternMnemonic*` constants in `internal/ui/dialog/state_filter.go` (Simple / auto shell L, Shell S, Regex R, FilesOnly Y, DirsOnly D, Case E, IncludeMeta M, OnlyMeta N, plus Filter-only Invert I and Select group-only FullPath H, and `FilterTypeMnemonics`). Both renderers and both key handlers use them, and `dialog.PatternAltIsMnemonic` derives the pattern-input pass-through from them.

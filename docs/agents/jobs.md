# Jobs

Background jobs live in `internal/jobs`; the transfer glue is `internal/jobbridge`; file operations are `internal/ops`. User-facing behavior: `docs/jobs.md`, `docs/background-scan-throttle.md`. Defaults for every `[jobs]` / `[operations]` key named here live in `internal/config/builtin.go` and `docs/config.md`.

## Job lifecycle and locking

- `jobs.State.mu` (`internal/jobs/state.go`) is the sole lock for lifecycle fields (`Status`, `FinishedAt`) and the ownership buckets (`active`, `waitingBlocker`, `pendingDequeued`, `finished`). Lock order: `State.mu`, then `Queue.mu` (pointer slice). `*Unlocked` queue helpers (`dequeueRunnableUnlocked`, `pauseQueuedJobUnlocked`, ...) require `State.mu`; exported `Queue` methods take `Queue.mu` themselves. `AllJobs()` / `MenuBarStripStatuses()` copy lifecycle fields under both locks and deduplicate by job ID (first bucket wins), because buckets overlap during blocker transitions. `AllJobs()` order is `collectAllJobsUnlocked`: `active`, `waitingBlocker`, `pendingDequeued`, the FIFO (run order, so queue up/down matches the screen), then `finished` newest first; finished jobs come last so an in-flight copy of the same ID wins the dedupe. The menu-bar strip uses its own order (`collectMenuBarStripJobsUnlocked`, finished oldest first).
- States: scanning, queued, paused, running, waiting-decision, completed, failed, canceled.
- **Transfer lease**: `transferLease` serializes copy/move/flatten/extract, one at a time. `Job.holdsTransferLease(other)` (`internal/jobs/job.go`) is true for all of those; a delete takes the lease only when its source roots overlap `other`'s sources or destination (`pathloc.TreesOverlap`, ancestors included). Disjoint deletes run concurrently with each other and with the lease holder.
- `State.active` is a set of running jobs. `leaseHolderUnlocked` returns the one lease holder; `ActiveJob()` and `SampleActiveJobThroughput` read it, so they keep reporting the transfer while deletes run. `cancelRun` is a `map[jobID]CancelFunc`. Each `runJob` context derives from `s.workerCtx` and is registered in `cancelRun` before the lease wait; after acquiring the lease (and once before waiting) `runJob` returns without flipping status if the job is finished or its context is done. `workerShutdown` joins goroutines via `s.jobWg` and skips blocking lifecycle emits when the worker is stopped. A run sets the job's final status under `s.mu` before it queues the terminal event, so a finished status does not mean the UI has seen it: `State.RunsInFlight` counts run goroutines that have not returned (each returns only after its terminal event is on `Events()`), which the app tests' `flushBackgroundJobs` waits on before its last drain.
- `pendingDequeued` holds jobs removed from the FIFO by `dequeueJob` but not yet in `active`, so `AllJobs()` never drops entries when several jobs are queued or resumed at once. Entering a blocker removes the job from `active`/`pendingDequeued` and any stray FIFO row.
- **Cancel** cancels the scan producer from every `CancelJob` branch (active, pending-dequeue, waiting-decision, queued, scanning) and from `workerShutdown`: a producer blocked sending into a full `PlanCh` outlives `scanning`, and would leak forever on a paused huge job. Blocker **Cancel** returns `jobs.ErrUserCanceled` so the job ends `canceled`, not `failed`.
- **Retry**: `State.RetryJob(id)` requeues a `StatusFailed` or `StatusCanceled` job (`Status.IsRetryable`) under the same ID via `Job.RetryClone()` (only enqueue-time spec fields carry over; progress, `PlanCh`, `Error`, timestamps, `PendingBlocker` start zero; a copy with `FailedItems` instead gets `Plan` = those items and their totals, so `NeedsPreScan()` is false and `jobbridge.TransferFunc`'s `job.Plan` path re-runs only the failed items) through the normal `AddJob` path. `jobs.resume` dispatches to `ResumeJob` for paused and `RetryJob` for failed and canceled jobs (`resumeOrRetrySelectedJob`). `Handler.SelectedJobStatus()` is the single source for the footer relabel (`menu.FunctionKeysJobsView`) and the leader-menu relabel (`openViewLeaderMenu`).
- **Error text**: `ops.RootFirstErrorText(err)` (`internal/ops/source.go`) renders `"<root cause>: <outer context>"` and is the single formatter for `Job.Error` and the `EventFailed` `Error` field. `Event.Err` (raw) is unaffected.
- Quit: `app.quit` confirms when jobs are active, paused, or waiting, or a run-for-each batch or captured user-menu run is in flight (`commandsBatchesInflight`; interactive/detached entries do not count). `app.quit-immediate` skips the dialog but still stops the worker. `jobs.cancel` is a `[jobs]` overlay key and only acts while the jobs view is focused.

## Task jobs

- `jobs.TypeTask` (`internal/jobs/task.go`) runs `Job.Task` (`jobs.Task`: `Title`, `Lease`, `Run(ctx, TaskReporter)`) instead of `TransferFunc`; `jobs.NewTaskJob(task, sources)` builds it queued and `apphandler/jobs` `Handler.AddTaskJob` enqueues it. `Sources` are the paths it works on, so path marks and volume contention apply as for a transfer.
- **Lease**: `holdsTransferLease` is false for a task; `runJob` instead locks `State.taskLeaseUnlocked(Task.Lease)`, one mutex per lease name, so one task per name runs at a time beside any transfer. `leaseHolderUnlocked`, `ActiveJob` and throughput sampling never see a task.
- **Reporting**: `runTask` hands `Run` a `taskReporter` (safe for concurrent use). `Progress(TaskProgress)` keeps the latest sample (`TotalFiles` never shrinks) and emits, at most every `ScanConfig.ProgressMinInterval`, `EventPlanTotals` when `TotalFiles` grew and then `EventProgress` (`DoneFiles`, `DoneBytes`, `CurrentPath`); `finish` flushes the last sample and its counts become the terminal event's totals. Nothing is emitted once the worker context is done. `Warn` appends to `Job.Warnings` under `State.mu`. `StartSource(i)` is `Job.StartSource`, so a task working through its sources one at a time drives the per-source file-list marks like a transfer.
- **Outcome**: a `context.Canceled` or `ErrUserCanceled` return ends the job canceled, another error failed (`Job.Error`), nil completed. `CancelJob` cancels the run context as for any active job.
- **fileindex tasks** (`internal/fileindex/tasks.go`, lease `fileindex.TaskLease`): `ScanTask` runs fileindex's `scan.Run` once per path, calling `StartSource` before each (one root's marks clear as it finishes; hashing parallelism stays within a path), with `MissingOnly`, the config.ini rules, `[fileindex].workers` (else config.ini's) and `config.FileIndexScanBatchFiles` per commit so a cancel lands quickly. `scanReporter` maps `scan.Reporter` onto `TaskProgress`, each run's counts added to the finished runs' (`next`): `Scan` sets `TotalFiles` (files to hash), a worker starting its next file counts the previous one done, `Speed` integrates bytes, `Hashed` and the end replace the estimates with committed counts, `Prune` shows the directory; `Log` lines and `Stats.Errors` go to `Warn`, capped at `config.FileIndexMaxWarnings` plus one `… N more` line; `Stats.Interrupted` returns `context.Canceled`. `PruneTask` resolves the path like the index records it, runs `PrunePath` with `checked` as `DoneFiles` and the removal log as warnings.
- **Not supported**: no pre-scan (`NeedsPreScan` is false), conflicts, undo or operation-log rows. `Type.Pausable` is false (`PauseQueuedJob` refuses, `pauseSelectedQueuedJob` says so) and `Type.Retryable` is false (`RetryJob` refuses, as for rename and undo). `CanceledItems` reports nothing for a canceled task. The jobs view shows `Task: <title>` under `Type:` and no `Destination:`; the menu-bar strip shows no speed pill for a task.

## Undo

- **Journal** (`internal/ops/undo.go`): `ops.UndoStep` is `UndoRemoveCreated` (a copy created `Path`; `Size`/`ModTime` are an `Lstat` taken right after the write) or `UndoMoveBack` (`From` was moved to `Path`). `ops.Options.OnJournal` fires from `copyDirItem` (only when it ran `Mkdir`; merging into an existing directory is not journaled), `copyLocalFile`/`copyFileTransfer`/the two symlink copies (at the final destination, so keep-both names are right) and `moveOne` (plain rename, including merge children, and a copy-fallback move as one step for its top-level source). Fallback copies and undo run with `OnJournal` nil. A keep-both cross-device move fallback picks its own free name and is not journaled; a Delete source move (destination kept, source removed) is not journaled either.
- **Collection**: `jobbridge.TransferFunc` collects steps for copy and move and emits one non-droppable `EventUndoJournal` (deferred, so a failed or canceled run still reports what it did). `State.ApplyEvent` appends to `Job.Undo` and sets `Job.Irreversible`; no other code writes them.
- **Irreversible**: `trackIrreversible` wraps the resolver from `newConflictResolver`, the only place overwrites are decided. An overwrite or delete-source answer (not downgraded by `OverwriteUnsafe`) marks the job irreversible; an identical answer keeps both files and does not. Such a job is never undoable.
- **State**: `Job.Undoable()` (finished copy/move/rename with a journal, not irreversible, not undone) and `Job.UndoLabel()` (Details `Undo:` line: available / irreversible / undone / nothing to undo). `State.EnqueueUndo(id)` is the only way to queue an undo: it re-checks `Undoable()`, refuses while an undo of that job is unfinished, and adds a `TypeUndo` job that copies the journal and mirrors the target's Sources/Destination, so path marks work and `holdsTransferLease` serializes it with transfers. `TypeUndo` and `TypeRename` are never retried (`RetryJob` rejects them). When an undo job completes or fails with at least one step done, `markUndoneUnlocked` sets `Undone` on its target.
- **Execution**: `ops.ExecuteUndo` walks the journal in reverse and checks each step first. `UndoRemoveCreated`: same kind, and for non-directories the same size and mtime; directories are removed only when empty. `UndoMoveBack`: the item must still be at `Path` with the same kind and `From` must be free; it then runs through `moveRun.moveAndCount` with an always-skip resolver, creating `From`'s parent if needed, so cross-device moves copy back and nothing is overwritten. Two or more local same-directory `UndoMoveBack` steps (a mass rename) go through one `ExecuteMassRename` so swaps and chains work; a step's target counts as free when another kept step vacates it. A failing step is reported through `Options.OnItemError` (`EventItemFailed`, built from a `PlanItem` with `Src` = the step's `Path`), so the job ends `failed` with `N item(s) failed` and the Operations pane lists the leftovers as failed rows.
- **Rename jobs**: `Handler.RecordRename` (`internal/apphandler/jobs`) adds a completed `TypeRename` job through `State.AddFinishedJob` (Sources = old paths, Destination = the parent directory, journal = `UndoMoveBack` steps). `dialogctrl` calls it from `applyRenameSuccess` (single rename, sync and remote/elevated paths) and `applyMassRenameRows` (mass rename OK and each Apply). No job event is emitted; the handler resyncs the list itself.
- **UI**: `jobs.undo` (`[jobs]` overlay, Jobs menu "Undo job", leader group Queue, footer **Undo** shown only for a finished selected job via `FunctionKey.RequiresFinishedJob`) calls `Handler.undoSelectedJob`, which opens `UndoConfirmState` (default No) or explains why the job cannot be undone; Yes calls `Handler.ConfirmUndo`. Not covered: flatten, delete, extract, a keep-both cross-device move, and persistence across restarts (jobs are session-only; retention drops the journal with the job).

## Scan (planning) and totals

- Only `TypeCopy` pre-scans (`Job.NeedsPreScan()`); move and flatten enter queued/paused directly. A move counts its copy phase in the background instead (see **Move**); `Job.CountsTotals()` is true for both. A copy leaves `scanning` as soon as the first plan item is known, so bytes move while the walks continue.
- `jobbridge.ScanFunc()` runs **two independent walks** (both `ops.BuildPlanStreamCtx`):
  - **Delivery walk** feeds `Job.PlanCh` through a bounded relay; the executor consumes it via `ops.ExecuteCopyUsingPlanChan` (same `executeCopyIter` loop as the slice path).
  - **Counting walk** tallies `files`/`dirs`/`totalBytes` and discards items.
  - They are separate because the relay blocks for as long as the executor spends on one item (e.g. a huge file) and totals tallied on that path would freeze. Totals emit via `EventScanTotals` at `[jobs].scan_progress_min_interval_ms`.
- `Job.PlanComplete` flips true when both walks finish. `PlanProducer.Err()` reflects only the delivery walk; a counting-only failure never affects the outcome. The counting walk runs with `OnWarning`/`OnPath` cleared (`countOpts`) so nothing is double-reported and `runJobScan`'s `lastProgress` has one writer. `Job.TotalsComplete` (counting walk done) is what the jobs view uses for the `(scanning...)` suffix, not `PlanComplete`.
- **Mid-stream enumeration errors** can land after real work happened. `runJobScan` (`internal/jobs/scan.go`) calls `finishScanFailed`/`finishScanCanceled` only if the job never left `scanning` (`alreadyFlipped`). Otherwise it just sets `PlanComplete` and final totals, and the executor ends the job `failed` via `job.PlanErr()` with completed work kept. This avoids two writers racing on `job.Status`.
- **Scan throttle** (`internal/jobbridge/scan_throttle.go`, `newAdaptiveThrottleYield`): both walks yield cooperatively per time slice (`newDutyCycleYield`: sleep `[jobs].scan_yield_interval_ms` after `scan_yield_work_ms` of walking; the walk checks the clock every `config.DefaultScanYieldCheckEveryN` entries), never via OS nice. Each walk builds its own duty-cycle instance (not goroutine-safe). The counting walk additionally runs a duty-cycle probe, only while the job's own EMA transfer rate (`ETABytesPerSec`, exposed as `ScanWalkHooks.ThroughputBPS`) is positive: it pauses the walk for a short window and compares throughput before vs. during. The probe wraps the counting walk's sleep, so it and its pause run once per time-slice sleep. A significant rise grows an injected per-sleep pause (`dutyPauseMS`, capped); no rise decays it toward zero. Evidence-based, no disk-type detection: on SSD/NVMe/network the pause never helps and stays at zero. Constants are `DefaultScanThrottle*` in `internal/config/builtin.go`; `[jobs].scan_disable_adaptive_throttle` turns the probe off.
- **Enqueue-time estimate**: `apphandler/jobs` `Handler.AddTransferJob` calls `applySizeEstimate`, which runs `ui.SourceSizeEstimates` over the sources (the same `pathImpact` rules as the panel's selection-size label: listing entries and off-listing metadata from the active panel, disk-usage cache via `Host.DiskUsagePainter`, a cached size for paths the lookup misses; no filesystem access). Callers enqueue **before** `ClearSelection`, which drops off-listing metadata. A copy takes any positive total as `Job.EstimatedBytes` and seeds `TotalBytes`; `runJobScan`'s `writeTotalsAndEmit` keeps `TotalBytes = max(counted, EstimatedBytes)` until `TotalsComplete`, then writes the exact count. A move takes the estimate only when every source is known, also setting `Job.SourceSizeHints` (aligned with `Sources`); its first `EventPlanTotals` carries `TotalBytes: EstimatedBytes`, the background count keeps it as a floor until complete, and `ops.ExecuteMove` credits a source's hint as `DoneBytes` only when the rename phase moved it whole (`ops.Options.SourceSizeHints`); bytes the copy phase copies are credited by the copier. `RetryClone` carries both fields, except a copy retried with `FailedItems` (its `Plan` totals are exact). The jobs view shows `(estimated)` while the total is the estimate (`jobTotalsEstimated`) and `(scanning…)` while a copy or move is still counting after leaving `scanning` (`jobStillScanningInBackground`); the menu-bar bar is indeterminate only while `CountsTotals() && !TotalsComplete` with no estimate.
- **Disk-usage feed**: a clean single-source, local, non-dereferencing copy publishes the counting walk's byte total to `State.sourceSizeSink` (`SetSourceSizeSink`, wired to `diskusage.Engine.SetSize` in `internal/app/app.go`). Move/flatten and dereferencing or multi-source copies never feed it (stale or out of scope).
- **Disk-usage cache feed** (ADR 0023): `jobbridge.TransferFunc` takes an `fschange.Sink` (the `diskusage.Engine`, wired in `internal/app/app.go`) and puts it on the job context with `fschange.WithSink`, next to `ops.WithElevator`. The ops primitives report what they did as they do it, so every job type (copy, move, flatten, delete with `DeleteRemoveEmptyDirs`, extract, undo) keeps scanned totals in step while it runs, failures and cancels included. The emission points are listed in `file-operations.md` (Filesystem change reports).
- **Plan fallback**: `ops.BuildCopyPlanWithTotals` (full `[]PlanItem`, consumed by `ExecuteCopyUsingPlan`) is the synchronous fallback `jobbridge.TransferFunc` uses only when `Job.PlanCh == nil`.
- **Item failures (copy only)**: a copy skips a failing item and carries on. Two sources, both reported through `Job.FailItem`, the one failure path (it records the failed Operations row and emits the non-droppable `EventItemFailed` with `Event.FailedItem`): the plan walk (`ops.PlanBuildOptions.OnItemError`, wired to `ScanWalkHooks.OnItemError` in `runJobScan`; unsupported file types such as sockets and FIFOs; the counting walk gets a no-op) and the executor (`ops.Options.OnItemError`, set by `jobbridge.TransferFunc` for `TypeCopy` only; a failure tagged by `localfs.SourceError` such as an unreadable or vanished source file, `skipSourceItemError` in `internal/ops/copy.go`). Destination write, ENOSPC, fsync, conflict-cancel and context errors still abort. Move keeps `OnItemError` nil because its copy fallback deletes sources afterwards. `Job.FailedItems` is written only by `State.ApplyEvent`; `State.emit` also counts `EventItemFailed` per job so `runJob` can end a job whose transfer returned nil as `failed` with `"N item(s) failed"` without waiting for the UI loop.
- `Job.Warnings` collects non-fatal plan issues (symlink-dereference fallbacks), appended under `State`'s lock from the producer's `OnWarning`. Only a non-empty `Error` fails a job, never `Warnings`. The Details pane renders `Warnings (N):` after `Error:` (`detailStaticLines`, `internal/ui/jobs_view_render.go`).

## Disk space

- Enqueue never walks or checks space (`file.copy` and the other transfer dialogs queue immediately; a pre-enqueue walk would block the UI thread). `ops.EnsureDiskSpace` runs at run time.
- The whole-payload upfront check runs only on the synchronous-rebuild fallback (`PlanCh == nil`). Streamed jobs skip it: `TransferFunc` cannot race-free read a still-streaming job's `TotalBytes`/`PlanComplete` (the producer writes them under `State`'s lock). The per-file check is the safety net (mc has no upfront check at all).
- Per-file check applies at or above `[operations].disk_space_check_min_file_bytes` (`0` = every file).

## Blockers

- File-exists conflicts and insufficient disk space share one mechanism: `jobs.EventJobBlockerRequest` + `jobs.BlockerDetails`. The worker **releases the transfer lease** while waiting so another job can run; `State.SubmitBlockerDecision` / `SubmitConflictDecision` resumes.
- Choices: File exists (overwrite / overwrite all / advanced rules / skip / skip all / delete source (move only, `ConflictRequest.Move`) / cancel), Disk space (retry / abort). When exactly one side is a directory (or a symlink to one; `ops.FileConflictFacts.Mismatch`) the prompt reads `Destination is a directory` / `Destination is a file`, hides Overwrite, Advanced and Delete source, and offers rename / rename all / skip / skip all / cancel; remembered overwrite-all and rule answers are ignored for it and the user is asked again (see ADR 0011).
- **Conflict rules** (`jobs.ConflictRules`, evaluated by `ConflictRules.Evaluate` in `newConflictResolver`): time row, then size row, then Ask. With `Verify` the resolver first gets a `jobs.ContentVerdict` from `contentVerifier` (`compare.SameContent`, the panel-compare check, with a read buffer allocated once per job; different size or a symlink is `ContentDiffer` without reading; computed once per conflict, kept across reprompts) and `Same` / `Differ` decide before the matrix; `Differ = RuleFallback` ("Rules") hands the file to the matrix. `ruleResolution` maps actions: Skip on a verified-same file is `ops.ActionIdentical`, Delete source is `ops.ActionDeleteSource`; Ask reprompts with a verdict note (`rulesRepromptNote`). `Normalize(move)` strips Delete source outside moves. Verification emits droppable `EventVerifyProgress` (`Job.VerifyDone`/`VerifyTotal`, the Details `Verifying:` line), throttled by `[jobs].worker_progress_min_interval_ms` and cleared by the next `EventProgress` or blocker request; its bytes never count toward `DoneBytes`.
- Surfaces: the jobs-view blocker panel above Details; the quick dialog `jobs.answer-blocker` (`PrimaryModalConflict` slot) which opens the oldest FIFO `waitingBlocker` job and adds **Postpone**; `[jobs].blocker_dialog_next_debounce_ms` auto-opens the next prompt after a real answer. Opening the jobs view (`jobs.open`) while a blocker waits selects the first such job and focuses the blocker panel. The menu bar shows a `status.waiting_input`-styled "N job(s) waiting" label before the permission tail.
- Alt+letter shortcuts match button shortcuts; Alt+R is disk-space Retry on the blocker panel. The quick dialog is a `dlg` spec (`ConflictDialogState.Screen`: File exists with its mismatch variant, Disk space, Conflict rules); its buttons are IDs (`dialog.ConflictOverwrite`, ..., `ConflictDeleteSource`, `ConflictCancelJob`, `ConflictPostpone`) that `dialog.ConflictDecisionOf` maps to decisions. `dialog.ConflictFileButtons` is the one button list: the jobs-view panel draws it minus Postpone (`ui.conflictPanelButtons`), its focus index is the position in that list, its rows follow `NewRow`, and its Alt letters are the buttons' mnemonics (`ui.JobBlockerPanelMnemonic`). The panel is an inline pane, not a modal: global view keys (`messages.open`, ...) are dispatched before it, so its mnemonics must avoid them (`dialogs.md`, Inline panes). The file prompt's strip is three rows (`Button.NewRow`; Delete source shares the last row with Cancel); Up/Down move to the button drawn nearest in the adjacent row and Tab leaves the strip. `jobs.Handler.HandleBlockerDialogKey` feeds `dlg.HandleKey` with the screen on top (`BlockerDialogScreen`: `ConflictDialogState.Focus`, `AdvFocus` on the rules screen); Enter on a rules-screen checkbox applies the rules, Space and the mnemonics toggle it.

## Copy and move execution (`internal/ops`)

- **Move** (`ExecuteMove`; flatten runs `ExecuteFlatten`, see [file-operations.md](file-operations.md)) runs in the style of mc, in two phases. The **rename phase** (`moveRun.collect`) goes over the top-level sources: resolve destination, run the shared `ConflictResolver`, try `RenameFastPathCtx`. A directory onto an existing directory **merges** (`collectMerge`: no prompt for the directory, children recurse, emptied source removed via `removeDirIfEmpty`); symlinks are never descended (`statEntry` is Lstat-based). What cannot be renamed is set aside as a `moveTask` (copy, or the `rmdir` of a merged directory after the work under it). `ops.Options.OnCopyPhase` then receives an `ops.MoveCopyPhase` and the **copy phase** (`runTasks`) runs the tasks in order. `moveAndCount` (flatten, undo) runs both phases for one entry.
  - `ops.ActionIdentical` writes nothing and keeps the source (skipped, `identical`), in copy and move alike. `ops.ActionDeleteSource` (move only) keeps the destination and removes the source: `renameSourceForMove` deletes it (counts as moved, reported `ops.ItemSourceDeleted` with reason `source deleted`); in a copy fallback the item counts as transferred (`copySourceDeleted`) so `finishMoveCopyPhase` removes it.
  - Overwrite replaces a non-directory with a non-directory only (`resolveConflict` turns an overwrite on a directory mismatch into skip). Local paths just `rename(2)` onto the destination; SFTP renames the original aside to `.paras-move-stash-N`, restores it if the rename fails or needs the copy fallback, removes it on success (SFTP v3 rename cannot replace).
  - Only a source whose rename cannot be used (cross-device/host) is planned (`fallbackPlanTarget`), disk-checked, copied via `executeCopyWithPlan` and removed (`finishMoveCopyPhase`). Renames are never rolled back; a rename-phase error ends the job before any copy runs, leaving set-aside sources in place.
  - Remote stat/rename/stash use the job `ctx` (backends via replaceable `backendFor`); local `os.Rename` is not context-aware.
  - `ops.Options.OnRemoveSources(true/false)` brackets each fallback removal; `jobbridge.TransferFunc` wires it to `EventRemovingSources` (`Event.Removing`) -> `Job.RemovingSources`, which drives the menu-bar delete gradient while it is on (see [architecture.md](architecture.md)).
  - Move progress units: one `DoneFiles` per top-level source moved by rename or merge (a merge with copied children counts when its `rmdir` task removes it) plus one per item the copy phase copies. `jobbridge.executeMove` announces `TotalFiles = len(Sources)` / `EstimatedBytes` up front; `MoveCopyPhase.Items`/`Bytes` are the rename phase's settled units and `MoveCopyPhase.Count` (nil when nothing needs copying) walks the copy tasks the way `moveCopyFallback` plans them. `startMoveCount` runs it beside the copy, emitting `EventPlanTotals` (Items + walked items, Bytes + walked file sizes, `max` with `EstimatedBytes` until done) every `scan_progress_min_interval_ms` and a final one with `TotalsComplete`. The count is unthrottled (metadata only, copy-phase sources only). `OnRemoveSources(true)` waits for the count, so totals are final before any source is deleted and the walk never races a removal; `executeMove` cancels and joins the count before returning, so no totals event follows the terminal one.
- **Copy details**: directory `chmod`/`chtimes` run after the full plan so children don't clobber parent mtimes; timestamps use real atime on Linux (`localfs.FileTimes`), remote sources use mod time for both. Symlink conflicts use `Lstat` on the destination; skipped symlinks and skipped conflicts do not count toward `DoneFiles`/`DoneBytes`.
- **Symlinks** are recreated as symlinks by default. `Job.DereferenceSymlinks` (`[operations].dereference_symlinks` / Copy dialog checkbox) copies through them like `cp -L`:
  - `localfs.WalkDirRecursiveDeref` `os.Stat`s each link in place; the `PlanItem` keeps the link's own path but is classified as the resolved kind, so the rest of the pipeline needs no special case.
  - Cycle detection uses the ancestor stack of the current recursion path (`os.SameFile`), not a whole-tree visited set, so sibling links to one shared target work; `maxSymlinkDerefDepth` (32) backstops long chains.
  - Anything not safely dereferenceable (broken, permission, cycle, depth cap) is recreated as a plain symlink and recorded in `Job.Warnings`.
  - Local-to-local Copy only: `AddTransferJob` (`internal/apphandler/jobs/handler.go`) decides the field and forces it false for Move; `jobbridge.buildTransferOptions` strips it whenever any endpoint is remote, with CoW, `copy_file_range`, sparse and preallocation.
- **Fast paths** (Linux, local only; remote endpoints disable them): `[operations].cow_file_cloning` tries `ioctl(FICLONE)` in `localfs.CopyFile`, then `[operations].copy_file_range` tries `copy_file_range(2)`, then falls back to `io.CopyBuffer`. One copy buffer (`[operations].copy_buffer_kib`) is allocated per job and passed through `localfs.CopyFile`/`copyFileTransfer`.
- **Durability**: `[operations].sync_after_each_file` fsyncs each destination before close. `[operations].sync_write_behind_mib` bounds the gap on filesystems that accept writes at memory speed (e.g. ZFS): `localfs.CopyFile` wraps `onWritten` and fsyncs every N MiB (`CopyFileOpts.SyncWriteBehindBytes`), reporting progress only after the flush. This keeps reported progress (and therefore the throughput chart, which decays idle columns to zero) honest. A mid-copy fsync error aborts immediately (`abortPartialLocalCopy`), since Linux reports fsync errors once per fd.
- **Progress and cancel**: byte-granular via `localfs.CopyFile`; `ExecuteCopy` throttles `EventProgress` (`[jobs].worker_progress_min_bytes` / `worker_progress_min_interval_ms`). Cancellation is checked per plan item, per buffered read, and per `copy_file_range` syscall (chunk-capped at `DefaultCopyFileRangeChunkMiB`); FICLONE is metadata-only.

## ETA and throughput

- ETA uses EMA-smoothed bytes/s and files/s (`jobs.ApplyProgressETA`); metadata-only steps advance the sample clock so later byte deltas aren't divided by absorbed time. `jobs.FormatETA` blends each rate toward the cumulative average and shows the longer of byte-based and file-based remaining. `jobs.ComputeQueueETAs` is cumulative across unfinished jobs.
- **Displayed speed is sampled on a fixed wall-clock grid, never on progress events.** `jobs.SampleThroughputColumns` (`internal/jobs/throughput_strip.go`) closes each elapsed `[jobs].throughput_chart_column_ms` column, spreads bytes moved over the columns actually elapsed, and feeds the instantaneous rate into one EMA, `DisplaySpeedBPS`. `App.adjustJobsThroughputChartColumnMS` (Details-pane `+`/`-` via `Host.AdjustJobsThroughputChartColumnMS`) re-times the column duration live: it clamps to `config.ThroughputChartColumnMinMS`/`MaxMS` in steps of `ThroughputChartColumnMSLiveStep`, calls `State.SetThroughputChart` and `restartThroughputChartTicker`; config is untouched. That single value drives both the Queue **Speed** column and the Details chart (one sample per closed column, newest on the right). Idle columns feed zero; a late tick replays all elapsed columns (bounded by strip capacity); a large batched `EventProgress` is spread across the columns it covers.
- The `App` ticker (`internal/app/throughput_chart.go`) fires at column/4 (floor 40 ms) via `throughputChartTickPayload`, so boundaries land on the wall clock; oversampled ticks are no-ops and only a closed column repaints. It runs even when `throughput_chart_enabled` is false, because it also clocks the Speed column. `State.SetThroughputChart` wires column, window and enabled flag at startup; disabled means no strip data in the jobs DTO and no graph.
- Rendering: `jobs.ThroughputChartColumnBuckets` + `internal/ui/throughput_graph.go` (btop-style braille, same 25-char `braille_up` map). Until the first column closes the UI shows "collecting samples".

## Rate limit

- One global `*RateLimiter` (`internal/jobs/ratelimit.go`, hand-rolled token bucket) on `State`: `SetTransferRateLimit(bps)` / `TransferRateLimit()`, `0` = unlimited, session-only (never written to config), applied to all transfers together. `State.Wait(ctx, n)` is passed into `internal/ops` as a plain `ops.RateLimiter` func via `jobbridge.TransferFunc`'s third parameter (set in `internal/app/app.go`), so `ops` never imports `jobs`.
- Throttle point: `ops.Options.RateLimit` in both `onWritten` closures of `copyRegularItem` (`internal/ops/copy.go`). Kernel fast-path copies report their whole size in one call, so they are throttled post hoc.
- Controls (`Handler.TryDispatch`/`adjustRateLimit`, Queue panel focused): `+`/`-` step by `rateLimitStepBPS`. From Unlimited, either key starts at the active job's effective throughput rounded to a step (`rateLimitNoJobStartBPS` when idle). `-` floors at one step and never falls to Unlimited; only `jobs.rate-limit-clear` or the Jobs menu item clears. None appear on the F-key bar.
- Display: the Queue panel's border end-label (`formatRateLimitLabel`, padded per the border-label rule in `dialogs.md`). `internal/app/render.go` refreshes `Model.JobsTransferRateLimitBPS` every frame.

## Jobs view and panel integration

- **Event draining**: job events are drained on key and `jobsWakePayload` only, not spinner/volume/chart interrupts. Progress events in a batch are coalesced to the last sample per job. In the browser, progress neither wakes the UI nor repaints the twin panels; the jobs view repaints. `syncJobsList()` runs while the jobs view is open.
- **Free space** uses async `statfs` (`[jobs].free_space_on_progress_wake`, `free_space_poll_interval_secs`). Panels on the same volume as an active job skip progress/ticker `statfs`; `Job.VolumeDevs` is computed once in `AddJob` (`ComputeVolumeDevs`: one stat per distinct source parent plus destination, not per source, because `AddJob` runs on the UI thread and per-source stats froze the app on network mounts). The suppression check runs inside the async goroutine so the UI thread never stats job paths. Menu-bar spinner: `DrawMenuBarSpinnerOnly` without draining the channel. Browser list paint runs `DiskScanExcluded`/`PendingForPanel` only when disk-usage metering is shown.
- **Layout**: `geom.SplitJobsView` (via `ui.JobsViewLayout`) is the one source of the pane frames (`JobsViewRects`: List, Conflict, Detail, Operations); drawing (`drawJobsView`, `jobsMaximizedPane`), Queue hit tests (`JobsListEntryAt`), Queue visible rows (`scrollToSelection`) and the handler's pane frames (`jobsPaneLayout`, which sizes the Operations window) all take it. Side layout: Queue fills `layout.Primary`; the right column is the optional blocker panel, Details, Operations (`geom.SplitJobsSecondaryPanels`). Details ends with Current then the throughput chart and takes only the height it needs; Operations takes the rest. Bottom layout (`Model.JobsOpsBottom`, seeded from `[jobs].operations_layout`, flipped for the session by `jobs.toggle-operations-layout` → `Handler.toggleOperationsLayout`, never written back): Operations spans the bounding rect of both columns (`geom.BoundingRect`, also `JobsMaximizedRect`) at the bottom; above it a band as tall as blocker plus Details need, at least `jobsOpsBottomMinBandH` (Operations keeps at least `jobsSubpanelMinFrameH`) holds the Queue (primary's width when side by side, half when stacked) and blocker/Details on the right; too short a band falls back to the side layout. Tab order is `ui.JobsPaneOrder`: list, blocker (when the selected job waits), Details, Operations; `JobsViewState.FocusPane` indexes that order. Details body colors come from `jobs.detail.*` (`label` for the `Label:` prefix, `plot` for braille chart rows, `text` otherwise). Details and Operations share one scroll helper (`scrollPane`: Up/Down, PgUp/PgDn, Home/End).
- **Operations recording** (ADR 0021): every item outcome goes to `Job.Ops` (`*oplog.Log`, created in `State.AddJob`, carried by `RetryClone`) through `Job.RecordOperation`, the single writer (label: `jobs.OperationLabel`, the destination relative to the job destination, else the source path). Sources: `ops.Options.OnItemDone` (copy file/symlink: done, `exists` on a resolver skip, `identical`, `ops.ItemSourceDeleted` (reason `source deleted`) in a move's copy fallback, which `RecordOperation` stores as a skipped record with `oplog.Record.SourceDeleted`, kept in the spill file's result byte; a skipped directory once, not its children; move/flatten: one row per top-level rename or skip, a copy-fallback per copied item; undo steps), the `onItem` hook of `ops.ExecuteDeletePaths` and `ExtractPlan.OnItem` (per archive, including failures; both `ops.ItemFunc`, so jobbridge passes `Job.RecordOperation` directly), and failures through `Job.FailItem` (the executor's `OnItemError` wired in jobbridge and the plan walk's in `runJobScan`). No job event carries per-item outcomes. The log spills past `[jobs].operations_memory_rows` to the session directory `oplog.NewSession(os.UserCacheDir())` set by `State.SetOperationLog` (startup sweeps dead sessions in a goroutine); logs close when jobs leave the state (`ApplyRetention`, `ClearFinishedArchive`, `Queue.ClearFinished`) and `workerShutdown` closes all and removes the session directory. A failure is superseded when its label later succeeds or fails again (retry keeps the same log). Each record carries `Source`, the index of the job source its item came from, which `Job.RecordOperation` copies from `ops.PlanItem.Source`. Producers set it, never a path lookup: `buildPlan` stamps each source's items and plan-walk failures (`sourceStamped`); executors keep the unexported `ops.Options.source` current (copy: per plan item; move/flatten: per source/root; undo: per step), which `Options.itemDone` and the undo journal (`UndoStep.Source`) carry; a move's copy fallback re-tags its lone-source plan; delete passes the path's index and extract `ExtractItem.Source` (its position in the job sources, kept when `PlanExtract` skips an archive); `RecordRename` numbers its steps. A retry keeps `FailedItems[].Item` and so its source. `oplog.Config.Sources` makes the log keep per-source result lists and counts (`Log.SourceStats`).
- **Operations pane** (`internal/ui/jobs_operations.go`): draws `Model.JobsOpsWindow` only (record rows `Offset..` newest first, `Total`, `Scanning`, and `Active`: the item in progress, display row 0 ahead of the records with `Theme.IconJobsList("running")` (`jobOperationActiveLine`), so it scrolls with them; `DisplayTotal` counts it and `RecordSpan` maps a viewport to the records it shows; `opsActiveLabel` sets it from `JobEntry.CurrentPath`/`CurrentDestPath`, the latter kept by `EventProgress` on `Job.CurrentDestPath`, worded by `jobs.OperationLabel`, only while the job runs or waits on a decision with no fuzzy query, result filter or other selected source, and not while the newest record is that item); `jobs.Handler.RefreshOpsWindow` (`internal/apphandler/jobs/operations.go`) builds it from `App.render` while the jobs view is open, rate limited: when the `opsInputs` (job ID, `opsViewKey`, scroll, content rows) match the last build, no row is `Pending` and less than `[jobs].operations_refresh_interval_ms` has passed, the window is kept and one trailing `sched.Debouncer` wake (`opsState.trailing`, armed only when idle) posts `OpsWakePayload` at the interval's end; any changed input (scroll, query, result filter, job or source switch, resize, maximize) rebuilds at once, and `scrollOperations` forces a rebuild (`refreshOpsWindow(true)`). A build is limited to `opsViewKey.source` (`JobsViewState.SelectedSource`; `oplog.NoSource` for all), which `Log.ViewLen`/`ViewNums`/`Scan` take, and the pane shows that source's label as its top-border end label. A query-less view takes `Log.ViewLen`/`ViewNums` for `JobsViewState.OpsResultShown().Mask()` (a `dialog.JobResultFilter`, whose bits are `oplog.Mask` bits, stored inverted as `OpsResultHidden`); a fuzzy query (`OpsFilter.Query`; case sensitivity from `Model.JobsFilterCaseInsensitive`) runs `Log.Scan` in a goroutine (restarted on a key change, continued over appended records) and pages through its matches, with ranges from `search.Query.Match` per drawn row. Rows come from `Log.RecordsInMemory`; rows only in the spill file are read by one `Log.ReadRecords` goroutine and render as `…` until it finishes; both goroutines post `OpsWakePayload`, which `App.handleInterruptPayload` turns into a jobs-view repaint (the plain `WakePayload` repaints only when job events changed something). `OpsScroll` counts display rows from the newest one to the viewport's newest edge (0 follows new rows), clamped to `ui.JobsOpsMaxScroll` over `DisplayTotal`; a rebuild of the same job and `opsViewKey` with `OpsScroll > 0` adds the change in `DisplayTotal` since the last build (`opsState.lastDisplayTotal`), since rows only come and go at the newest edge, so a scrolled viewport stays on its rows; `refreshOpsWindow` zeroes it whenever Operations is not focused (the one reset for Tab, clicks and pane changes). Row order: `Model.JobsOpsNewestLast` (from `[jobs].operations_order`) makes `drawJobsOperationsPanel` draw the visible rows reversed, newest on the last line, a short list top-aligned (with wrap the oldest row is cut at the top); the scroll model is unchanged and `scrollOperations` (which refreshes the window first) swaps Up/Down, PgUp/PgDn and Home/End through `opsNewestLastKey`. Rows: one-cell result icon (`Theme.IconJobsOperation` keyed by `ui.JobOperation.IconKey`, which is the result key except `source_deleted` for a `SourceDeleted` row; style `JobsOperationOn` keyed by `ui.JobOperationResultKey`), the label, then `": <reason>"` in the result style for skipped and failed rows (`fitJobOperation`: the label is path-fitted keeping at least half the width, the reason truncated on the right); fuzzy ranges in `fuzzy.highlight` (skipped on fitted or wrapped rows). While a query is set or editing, `> query` replaces the title at the top left of the border (`drawFuzzyQueryTitle`, the renderer `drawQuickFilterTitle` also uses; caret while editing in the focused, unblocked pane; `fuzzy.input.nomatch` when the finished view is empty), shown when unfocused too since it still filters. The bottom border shows the result label unless All and `filtering…` while a scan runs (`drawAuxPanelBottomCenterSpans`).
- **Details counts**: `JobEntry.OpsStats` (from `Log.Stats` at list sync) feeds the Details `Files:` line, `N done, N failed, N skipped` with failed and skipped in their `jobs.operations.*` styles and zero counts omitted, then for a canceled job `N canceled`, `canceled: incomplete scan` or `canceled: unsupported` in the `jobs.operations.skipped` style (`jobs.CanceledItems`: a copy whose totals are final (counting walk finished, or a failed-items retry, whose `RetryClone` sets `TotalsComplete` from `SummarizePlan`) counts files like the rows do: `TotalFiles - TotalDirs - Job.ProcessedItems` (the `Progress:` line's items include directories, so the two lines differ by the directories); delete, extract and undo subtract their recorded rows; a copy canceled mid-scan and every move (no counting walk) are `CanceledUnknown` (`canceled: incomplete scan`); flatten is `CanceledUnsupported` (`canceled: unsupported`); the line shows even with no rows). `ProcessedItems` comes from `ops.Options.OnItemsProcessed`, called once when `executeCopyIter` returns with every non-directory plan item it went through (`countProcessed`: written, skipped, failed, and the files under a skipped directory, which have no row; directories excluded by `IsDir`, the counting walk's `TotalDirs` rule); jobbridge's `runTransfer` puts it on the final `EventProgress`, `runJob` copies it onto the terminal event, and `finalizeJob` stores it, plus `(log incomplete, N dropped)`; `jobFilesLineParts` is the one source of its text and spans.

  - **Matching** (`internal/ui/job_path_marks.go`): rows under any job source or per-source resolved destination root match. `newJobPathIndex` resolves destinations from `Job.DestIsDir` plus a plain `Join` fixed at enqueue and **must never Stat** (render-critical). Overlap precedence: type (delete > extract > move > copy), then longest root, destination on ties; finished jobs skipped. The index maps each root to its source index, so a multi-source job's marks follow the executor: `JobPathMark.SourcePhases`/`ActiveSource` (`Job.SourcePhases`/`ActiveSource`, refreshed in place by `SetJobPathMarkSources` from `followActiveSource` on progress events whenever `Job.SourceVersion` moves) give each root a `rootPhase` while the job is active and a source has started: the started source's roots are active (job icon), a not yet started source's source root is pending (queued icon) and its destination unmarked, a finished source's roots unmarked; the walk skips unmarked roots and continues outward. Single-source jobs, jobs before their first source starts and non-active jobs mark every root as active. Matching is **O(path depth)**: the index holds normalized sources, deduped source parent dirs and resolved destinations, and `longestMatchingRootLen` walks the row path's ancestors. A linear scan once cost ~135k `filepath.Rel` per frame at 3000 sources and froze the UI.

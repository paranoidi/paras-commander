# Create a new dialog

**`docs/agents/dialogs.md` is the source of truth** — navigation rules, button shortcuts, spacing (label → content, compact: no blank row between a label and what it labels), one-blank-row-above-buttons, geometry helpers, styling. Read it first; this file is only the wiring checklist.

## Wiring checklist

**Prefer the `dlg` engine** (`internal/ui/dialog/dlg`, ADR 0020) when the dialog is only radios, checkboxes, static text rows, separators, text inputs, plain lists and a button strip (OK/Cancel or custom buttons): write `XView(state) dlg.Spec` (state `Focus` is a `dlg.ID`), an `Apply(dlg.Event)` method on the state when it has radios or checkboxes, make `DrawX` one `dlg.Draw` call, and let the key handler call `dlg.HandleKey` (see `SortDialogView` / `App.handleSortDialogKey`, or `UndoConfirmView` for a message with custom buttons). Use `dlg.KindLabel` items for message lines (`Indent`, `Fit`, `Prefix`, `Style`, `Center` for the variants), `dlg.KindSeparator` for section rules and `Spec.Unclamped` for modals that must always draw. A text input is a `dlg.KindInput` item (`fileFieldInput` builds one from a `FileDialogField`): keep the text in the state, copy it into the item in the View, and after `dlg.HandleKey` declines a key feed it to the existing text-editing code; the key contract is in `dialogs.md` (Declarative dialogs, Inputs). An overlay anchored to an input (completion dropdown) is painted after `dlg.Draw` from `Placement.Item(id)`. A list is a `dlg.KindList` item: keep the rows' source data, cursor and offset in the state, copy them into the item in the View (the View takes the layout to pick `Height`), apply every `dlg.EventListMove` to the state, and make a filter input drive it with `Item.Drives` plus `Driven` on the list (key contract in `dialogs.md`, Declarative dialogs, Lists). A preview pane or row icons are painted after `dlg.Draw` into a `dlg.KindSpacer` item's rect or from labels' rects. Geometry, focus order, Tab groups, mnemonics and mouse hit-testing then come from the one spec, and items 3, 5 and 6 below are handled by the engine. Items 1, 2 and 7 still apply (item 7: map the central OK / Cancel chords onto the dialog's own button IDs). Add render and key-script goldens for the dialog (see `dialogs.md`, Declarative dialogs). Dialogs whose lists need per-row icons, marks or columns (history, pin, path picker, find), a large custom widget or inline-labelled option rows use the hand-written path below.

1. **State + render**: dialog state struct and `Draw*Dialog` in `internal/ui/dialog/` (`*_dialog_render.go`), always held in `ui.Model` regardless of which package opens/drives the dialog. Modal orchestration/focus for most file-operation and navigation dialogs lives in `internal/apphandler/dialog` (see `architecture.md` → Package layout for exactly which dialogs stay in `internal/app` instead — settings/config-edit/theme/debounce-calibrate, SFTP, history, quit/stash); `internal/app/input.go` still owns the InputMode enum and top-level key-dispatch priority switch, forwarding to `a.dialogCtrl.*` (or the app-side handler for dialogs that stay there). File dialogs use `FileDialogState` with `FocusedField` (button indexes = `len(Fields)+0` OK, `+1` Cancel).
2. **Label spacing guard**: every labelled input/value row is covered by `TestDialogLabelsAreFollowedByContentRow` (`internal/ui/dialog/dialog_label_spacing_test.go`), which renders the dialog and asserts the row directly under each label holds its content (compact layout — no blank row between). Add a case there for the new dialog's labels.
3. **Geometry**: use `draw.DialogTextX(rect)` (labels/inputs, `rect.X+2`), `draw.DialogOptionX(rect)` (checkbox/radio helpers, `rect.X+1`), `draw.DialogContentWidth(rect)` — never re-derive offsets. Flow `y` downward and size `height = y - rect.Y + 2`; don't anchor buttons in an oversized fixed height.
4. **Inputs**: `FileDialogField` rows via `drawInputField` (prefill/placeholder semantics, `ui.input.restore-default` restore, horizontal scroll); simple strings via `drawSimpleDialogInput`; fuzzy/filter rows via `App.handleScrollingQueryKey` + `DrawScrollingDialogInput`. Path fields: set `PathPicker: true` to get the `bookmark.open` / `panel.history-dialog` host shortcuts + ghost completion (no trailing icon; the field uses the row's full width).
5. **Styling**: `DialogSurface` fill, `DialogInputPair(focused)` for input rows, `DialogOptionRowStyle` for radios/checkboxes, `drawDialogButton()` for buttons (`DialogButtonActiveDestructive` for destructive focus). Checkbox/radio marker icons come from `Theme.IconDialogCheckbox`/`IconDialogRadio`, gated by `UI.UseNerdfontIcons` (forces ASCII when off). **No navigation help footer rows.** Radio rows are **focus-only** on Up/Down/Tab navigation — **Space** or **Enter** commits the focused radio (same as checkbox toggle); Alt+letter mnemonics still select directly.
6. **Dialog-local shortcuts**: put them in a `[dialog.*]` overlay (`internal/keymap/*_dialog_overlay.go` + allowed-identifier validation) — see `add-keybinding.md`. Standard nav (Up/Down/Tab/Left/Right/Enter/Esc, Alt+letter button shortcuts) comes from the shared focus machinery: Up/Down step item-by-item, **Tab/Shift+Tab jump between control groups** declared with `DialogTrailingButtonsForm.WithSegments` — and **each text input is its own group**, so a dialog with two or more text inputs Tabs from one input to the next before leaving the block.
7. **OK / Cancel**: add one case to `App.activeDialogButtons` (`internal/app/dialog_buttons.go`) returning the dialog's OK / Cancel funcs (plus `Esc` only if Esc must differ). Do not handle the OK / Cancel chords in the dialog's key handler: `ui.input.dialog-ok` / `dialog-cancel` are dispatched centrally. Sub-phases and sub-confirms get exported `OK`/`Cancel` methods on their handler that pick the layer. Extra mnemonics (Alt+Y on a confirm) use `dialog.TryDialogMnemonics`.
8. **Blocked chrome**: modal open ⇒ panels render `panel.blocked.*` automatically; transient status messages paint **after** overlays.
9. **Background-updating dialogs** (progress, size scans): repaint the overlay only (Find/Delete pattern, e.g. `paintDeleteDialogOverlay`) instead of full `ui.Render` per tick.
10. **Verify**: `golangci-lint run ./...`, `go test ./...` (drive dialogs via `App.handleKey`, or call `App.reconcileAfterEvent()` when bypassing it); use random-word filenames in tests, never personal paths.

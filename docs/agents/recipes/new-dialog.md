# Create a new dialog

**`docs/agents/dialogs.md` is the source of truth** — navigation rules, button shortcuts, spacing (label → content, compact: no blank row between a label and what it labels), one-blank-row-above-buttons, geometry helpers, styling. Read it first; this file is only the wiring checklist.

## Wiring checklist

**Prefer the `dlg` engine** (`internal/ui/dialog/dlg`, ADR 0020) when the dialog is only radios, checkboxes, static text rows, separators, text inputs, plain lists, horizontal rows of those and a button strip (OK/Cancel or custom buttons): write `XView(state) dlg.Spec` (state `Focus` is a `dlg.ID`), an `Apply(dlg.Event)` method on the state when it has radios or checkboxes, make `DrawX` one `dlg.Draw` call, and let the key handler call `dlg.HandleKey` (see `SortDialogView` / `App.handleSortDialogKey`, or `UndoConfirmView` for a message with custom buttons). Use `dlg.KindLabel` items for message lines (`Indent`, `Fit`, `Prefix`, `Style`, `Center` and `Style` (`TextError`, `TextMessageError`) for the variants), `dlg.KindSeparator` for section rules and `Spec.Unclamped` for modals that must always draw. A text input is a `dlg.KindInput` item (`fileFieldInput` builds one from a `FileDialogField`): keep the text in the state, copy it into the item in the View, and after `dlg.HandleKey` declines a key feed it to the existing text-editing code; the key contract is in `dialogs.md` (Declarative dialogs, Inputs). An overlay anchored to an input (completion dropdown) is painted after `dlg.Draw` from `Placement.Item(id)`. A list is a `dlg.KindList` item: keep the rows' source data, cursor and offset in the state, copy them into the item in the View (the View takes the layout to pick `Height`), apply every `dlg.EventListMove` to the state, and make a filter input drive it with `Item.Drives` plus `Driven` on the list (key contract in `dialogs.md`, Declarative dialogs, Lists). List rows carry plain data for icons (`ListRow.Icon`), the invalid-path variant (`ListRow.Missing`), pinned / job marks (`ListRow.Marks`, `Item.MarksAfterText`, `Item.MarksWidth`) and pre-fitted column grids (`dlg.FitNone`); see `HistoryDialogView`, `PinDialogView` and `PathPickerView`. A preview pane, a completion dropdown, label icons or a bespoke scrolling body (command output, help entries: see `CommandOutputDialogView` and `HelpDialogView`, whose motion keys the caller handles before `dlg.HandleKey`) are painted after `dlg.Draw` into a `dlg.KindSpacer` item's rect, from an input's or label's `Placement.Item` rect. Geometry, focus order, Tab groups, mnemonics and mouse hit-testing then come from the one spec, and items 3, 5 and 6 below are handled by the engine. Items 1, 2 and 7 still apply (item 7: map the central OK / Cancel chords onto the dialog's own button IDs). Add render and key-script goldens for the dialog (see `dialogs.md`, Declarative dialogs). Several widgets on one line (a label and its radios, a checkbox grid with per-column offsets, two inputs side by side, a right-aligned preview) are a `dlg.KindRow` item whose `Cells` have `Width` / `Grow` / `Gap` / `Right` rules; `Item.Seg` makes cells or items of one group separate Tab stops, `Item.Disabled` greys out and unfocuses a radio or checkbox, `Item.EntryLast` picks the cell Up lands on, and a View whose rows follow the theme's marker icons takes the marker width and sets `Spec.MarkerWidth` (callers pass `dlg.MarkerWidth(styles)`, see `PreviewSettingsDialogView`, `patternSpec`), so the key handler and the mouse table build the drawn geometry. A progress meter is a `dlg.KindBar` item (`Frac` + `Label`), a multi-row button strip uses `Button.NewRow`, and a row of choices where some are greyed uses `Disabled` cells with `Item.FallbackFirst` (see `DedupProgressView`, `ConflictDialogView`, `ConfigDialogView`). Dialogs whose lists need per-column right-aligned fields or per-row painter colours (find), or a large custom widget, keep that part in a bespoke painter drawn into a reserved `dlg.KindSpacer` region after `dlg.Draw` (the mass rename preview, the delete list, the help list), so focus, Tabs, mnemonics and buttons still come from the spec.

1. **State + render**: dialog state struct and `Draw*Dialog` in `internal/ui/dialog/` (`*_dialog_render.go`), always held in `ui.Model` regardless of which package opens/drives the dialog. Modal orchestration/focus for most file-operation and navigation dialogs lives in `internal/apphandler/dialog` (see `architecture.md` → Package layout for exactly which dialogs stay in `internal/app` instead — settings/config-edit/theme/debounce-calibrate, SFTP, history, quit/stash); `internal/app/input.go` still owns the InputMode enum and top-level key-dispatch priority switch, forwarding to `a.dialogCtrl.*` (or the app-side handler for dialogs that stay there). A new file-operation dialog with `FileDialogField` inputs extends `FileDialogView` (its `Focus` is a `dlg.ID`, inputs are `FileFieldID(i)`).
2. **Label spacing guard**: every labelled input/value row is covered by `TestDialogLabelsAreFollowedByContentRow` (`internal/ui/dialog/dialog_label_spacing_test.go`), which renders the dialog and asserts the row directly under each label holds its content (compact layout — no blank row between). Add a case there for the new dialog's labels.
3. **Geometry**: use `draw.DialogTextX(rect)` (labels/inputs, `rect.X+2`), `draw.DialogOptionX(rect)` (checkbox/radio helpers, `rect.X+1`), `draw.DialogContentWidth(rect)` — never re-derive offsets. Flow `y` downward and size `height = y - rect.Y + 2`; don't anchor buttons in an oversized fixed height.
4. **Inputs**: `FileDialogField` rows via `drawInputField` (prefill/placeholder semantics, `ui.input.restore-default` restore, horizontal scroll); simple strings via `drawSimpleDialogInput`; fuzzy/filter rows via `App.handleScrollingQueryKey` + `DrawScrollingDialogInput`. Path fields: set `PathPicker: true` to get the `bookmark.open` / `panel.history-dialog` host shortcuts + ghost completion (no trailing icon; the field uses the row's full width).
5. **Styling**: `DialogSurface` fill, `DialogInputPair(focused)` for input rows, `DialogOptionRowStyle` for radios/checkboxes, `drawDialogButton()` for buttons (`DialogButtonActiveDestructive` for destructive focus). Checkbox/radio marker icons come from `Theme.IconDialogCheckbox`/`IconDialogRadio`, gated by `UI.UseNerdfontIcons` (forces ASCII when off). **No navigation help footer rows.** Radio rows are **focus-only** on Up/Down/Tab navigation — **Space** or **Enter** commits the focused radio (same as checkbox toggle); Alt+letter mnemonics still select directly.
6. **Dialog-local shortcuts**: put them in a `[dialog.*]` overlay (`internal/keymap/*_dialog_overlay.go` + allowed-identifier validation) — see `add-keybinding.md`. Standard nav (Up/Down/Tab/Left/Right/Enter/Esc, Alt+letter button shortcuts) comes from the shared focus machinery: Up/Down step item-by-item, **Tab/Shift+Tab jump between control groups** (the engine; `Item.Seg` splits a group) — and **each text input is its own group**, so a dialog with two or more text inputs Tabs from one input to the next before leaving the block.
7. **OK / Cancel**: add one case to `App.activeDialogButtons` (`internal/app/dialog_buttons.go`) returning the dialog's OK / Cancel funcs (plus `Esc` only if Esc must differ). Do not handle the OK / Cancel chords in the dialog's key handler: `ui.input.dialog-ok` / `dialog-cancel` are dispatched centrally. Sub-phases and sub-confirms get exported `OK`/`Cancel` methods on their handler that pick the layer. Extra mnemonics (Alt+Y on a confirm) use `dialog.TryDialogMnemonics`.
8. **Mouse**: add one case to `App.activeDialogMouse` (`internal/app/dialog_mouse.go`) returning the spec as drawn and a pointer to the dialog's focus field; clicks then replay the dialog's own keys (`dialogs.md`, Mouse). No mouse code in the dialog itself.
9. **Blocked chrome**: modal open ⇒ panels render `panel.blocked.*` automatically; transient status messages paint **after** overlays.
10. **Background-updating dialogs** (progress, size scans): repaint the overlay only (Find/Delete pattern, e.g. `paintDeleteDialogOverlay`) instead of full `ui.Render` per tick.
11. **Verify**: `golangci-lint run ./...`, `go test ./...` (drive dialogs via `App.handleKey`, or call `App.reconcileAfterEvent()` when bypassing it); use random-word filenames in tests, never personal paths.

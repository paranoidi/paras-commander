# Dialogs are described by a declarative Spec, drawn and driven by one engine

A dialog built on `internal/ui/dialog/dlg` is a plain-data `Spec` (widgets, Tab groups, mnemonics, buttons) returned by a pure `View(state) -> Spec` function, Elm style. State stays in `ui.Model` exactly as before; the engine owns no state beyond the focused widget ID. `dlg.Place` is the single layout pass, and `Draw`, `HitTest`, `Click` / `Wheel` and `HandleKey` all derive from the same `Spec`/`Placement`, so painting, focus order, Tab segments, mnemonics and mouse hitboxes cannot drift apart (a hand-written dialog would keep these in separate render, focus-index and key-handler code, which is what the engine replaces).

The engine reports activations as `Event{ID}` values rather than calling back: the caller maps a radio or checkbox event onto its state (`SortDialogState.Apply`) and treats `dlg.OK` / `dlg.Cancel` as it always did. This keeps the spec serializable, which is what future plugin-defined dialogs and mouse support need; there are no interfaces or closures in `Spec`.

Every dialog runs on the engine: those whose widgets it supports (radios, checkboxes, static text rows, separators, text inputs, lists, horizontal rows of those, reserved overlay regions, progress bars, a button strip of one or more rows) are described by their `View`, and one `FileDialogState` carries every file dialog (`Focus` is a `dlg.ID`; the run-for-each and mass rename picker sub-screens keep a `Focus` of their own). There are no index-based focus helpers left. The sort dialog was the pilot; the dialogs listed in `dialogs.md` followed. Text inputs are placed and drawn by the engine but edited by the caller: the text stays in the dialog state and `HandleKey` hands every editing key back, so the existing editing, completion and path-picker code is reused unchanged. OK/Cancel/Esc chords stay resolved centrally by `App.activeDialogButtons`; the engine never handles them. See `dialogs.md` (Declarative dialogs). Lists follow the same split: the rows, cursor and scroll offset stay in the dialog state, the engine owns the motion (so the keyboard and the mouse wheel share one implementation) and reports it as `EventListMove` events the caller stores; a filter input steers a list through `Item.Drives` without taking focus away from the input. Rows follow the same plain-data rule: a `KindRow` item holds `Cells` with width rules (fixed, content, grow) and its focus rules (Left/Right along the row, Up/Down by cell index, `Item.Seg` Tab stops) live in the engine, so the filter-style grids and the inline-labelled capability rows need no per-dialog focus code.

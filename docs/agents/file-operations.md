# File operations

Foreground dialogs and their execution. Handlers live in `internal/apphandler/dialog` (`dialogctrl.Handler`); execution in `internal/ops`; queueing in [jobs.md](jobs.md). User-facing behavior: `docs/fileoperations.md`, `docs/mass-rename.md`, `docs/elevation.md`.

## Source resolution and snapshots

- Source rule: selected entries first, else the cursor entry. Single-entry dialogs use `ResolveSourceSingle` and reject a non-empty selection where it applies.
- Delete and rename operate on the **snapshot taken at open** (`DeleteEntries`, `RenameSource` from `OpenDeleteDialog`/`OpenRenameDialog`), not the later cursor. `[operations].confirm_delete=false` still snapshots, then enqueues without a dialog.
- Successful mutations refresh both panels and try to keep the cursor on the affected entry. Same-directory reloads (`panel.State.Refresh`, `ApplyPeriodicRefresh`, `ToggleHidden`) keep `ScrollOffset` when the highlight row index is unchanged. If the inactive panel's cwd was removed, `RefreshBothPanels` (`internal/apphandler/dialog/file_ops.go`) climbs it to the nearest existing ancestor in one step (`RefreshOrNavigateToExistingAncestor`). Rename/mkdir/mass-rename patch `Entries` in memory (see [panels.md](panels.md)); jobs do not. `RefreshBothPanels` re-runs quick view from each panel's `OnApplied`.

## Dialog input

- Form focus: every file dialog (rename, duplicate, mkdir, delete, chmod, chown, symlink, hardlink, add bookmark, SFTP password, extract, run-for-each, mass rename) is a `dlg` spec dialog (`FileDialogView`, `FileDialogState.Focus`; see [dialogs.md](dialogs.md)): each text input is a Tab segment, the mkdir radios / rename checkboxes / run-for-each options are one group each, the buttons the last. OK runs the dialog whichever widget has focus (`Handler.FileDialogOK`; the extract and run-for-each executors read the first field, not the focused one).
- Input editing defaults live in `DefaultDialogInputOverlayKeys` (override under `[dialog.input]`): clear (`ui.input.kill-line`; `ui.input.kill-line-backward` also clears fuzzy rows), restore default (`ui.input.restore-default`), `ui.input.kill-word-backward`, word motion (`ui.input.backward-word` / `ui.input.forward-word`). Word boundaries: letters/digits/underscore (`internal/ui/lineedit`).
- Single entry points: `dialog.TryDialogInputFieldActions` and `dialog.HandleFileDialogFieldKey` (`internal/ui/dialog/dialog_field.go`) for `FileDialogField` rows (used by `apphandler/dialog` and the app-side SFTP-connect dialog). `App.handleScrollingQueryKey` (`internal/app/scrolling_query.go`) over `scrollquery.HandleKey` plus the `ScrollingQuery` type (`internal/ui/dialog/scrolling_query.go`) cover every fuzzy-filter row (path picker, Help, Find, History, SFTP connect, mass-rename pickers, run-for-each history, panel Filter / `panel.select-group` group select, `preview.theme-picker` style picker).
- Fuzzy-filter rows paint a leading search icon inside the row instead of a `Filter:` label row (`draw.ScrollingInputState.LeadingIcon`, `Theme.IconSearchIcon()`, `[icons.search] icon`, ASCII `/` fallback; painted by `draw.PaintScrollingInputContent`). Filter and group-select keep a blank spacer and right-aligned match count (`filterPreviewText`/`groupSelectPreviewText`); the style picker has no label row.
- Horizontal scrolling and `◀`/`▶` overflow icons: `EnsureScrollInputVisible` (`internal/ui/dialog/internal/draw/chrome.go`), `DrawScrollingDialogInput`, `drawInputField` (see [navigation.md](navigation.md)). `fileDialogWidth` floors at `PreferredFormDialogWidth` and sizes from labels/static messages/mkdir radios, never from field values, so the frame doesn't resize while typing.

## Rename and mass rename

- `Handler.renameTargetPanelID` is the one source of the panel a rename acts on: the focused column's panel in Compare ([views.md](views.md)), otherwise the active panel. `applyRenameSuccess` uses the `panelID` recorded in `renameApply`, because an elevated retry finishes later. It also carries the selection to the new path itself, since `panel.State.RenameEntry` returns early for a path outside the listing (a nested Compare row).
- Rename and mass rename stay synchronous. Each success is recorded as a finished `rename` job so it appears in the jobs view and can be undone with `jobs.undo` (see [jobs.md](jobs.md), Undo).
- `file.rename`: no selection opens single **Rename** (same directory only; rejects path separators and non-UTF-8 results). **Focus after rename** (M-a, `[operations].rename_focus_after`) selects and centers the new name via `SelectVisibleEntryCentered`. `file.rename.open-sanitize` / `file.rename.open-slugify` / `file.rename.open-encoding` (`[dialog.rename]`) open Sanitize / Slugify / Encoding sub-dialogs; Encoding appears only when `filenameenc.DetectCandidates` finds legacy Japanese encodings and previews the decoded name.
- On a `fileindex://` panel rename and delete change the index only: `ops.ExecuteRename` and `ExecuteDeletePaths` give the `fileindex://` path to the fileindex backend, the disk is not touched, and the dialogs carry `FileDialogState.Note` saying so ([navigation.md](navigation.md), Operations on fileindex:// paths). On a Browse-with panel real entries act on the disk and ghost rows only leave the index. The dialog's `fsCtx` includes the index sink (ADR 0028), the elevated retry included; a mass rename on a Browse-with panel reports through the same context. Mass rename refuses any non-local panel.
- Copy, move, flatten and extract on a `fileindex://` panel: copy out to a real directory works and a move inside the index renames records; a move out, a copy or move into the index and an index-to-index copy are refused by `Handler.indexTransferRefusal` (`AddTransferJob`; the transfer dialog stays open), flatten with any `fileindex://` root or destination is refused by `ops.ValidateFlattenTarget`, and an extract with a `fileindex://` destination is refused by `ExecuteExtract` (an indexed archive extracts to a real directory, its source translated with `pathloc.Path.Local`). The wording is defined once in `internal/ops` (`IndexReadOnlyRefusal`, `IndexMoveOutRefusal`, `FlattenIndexRefusal`). `TransferDialogState.SourceIsRemote` is true on a `fileindex://` panel (not `IsLocal`); `ops.SelfTargetCount` still translates, so copying an index entry onto its own file is caught.
- A non-empty selection in the current directory opens **Mass rename** (`ui.FileDialogMassRename`). Pure logic: `ops.MassRenameCompute` / `MassRenameComputeCapitalize` / `MassRenameRowErrors` / `MassRenameValidateRows` / `ExecuteMassRename` (`internal/ops/mass_rename.go`); duplicates, external collisions and illegal results are validated, and renames apply via a two-phase temp rename for dependency chains. OK stays focusable but Enter / `ui.input.dialog-ok` show a critical message while conflicts exist. Theme: `[dialog.massrename]` `dialog.massrename.*`; match-count icon `[icons.mass_rename] match`.
- Modes (the mode radios; Space or the mnemonic selects, Enter selects and moves to Show only modified): Simple (literal replace per basename), Regex (Go `regexp`, `$n`/`${n}`, `\1`-`\9` aliases), External `$EDITOR` (`MassRenameModeUIExternalEditor`: temp file one name per line, `withTerminalReleased`, line count must match, result in `MassRenameExternalNames`, OK blocked until set, Enter relaunches), Capitalize (`MassRenameModeUICapitalize`: **Capitalize each word**, **Treat punctuation as separators** which auto-enables the former). External and Capitalize take every preview highlight (before removed / replaced, after added) from `dialog.MassRenameDiff` (`internal/ui/dialog/mass_rename_diff.go`, LCS alignment: an old gap opposite a new gap is replaced, an old gap alone removed); Simple and Regex take them from `ops.MassRenamePreviewRanges`: Simple highlights each match and its replacement whole, Regex aligns each match with its expansion on the capture groups copied in order (`massRenameExpandSegments`, the single template expansion), so only the gaps between them highlight, classified like the diff.
- **Focus** (`FileDialogState.Focus`, a `dlg.ID`): the mode radios `MassRenameRadioID(mode)`, the option checkboxes `MassRenameOpt*`, the inputs `FileFieldID(0)` (Find / Pattern) and `FileFieldID(1)` (Replace / Replacement), the buttons `dlg.OK`, `MassRenameApply`, `dlg.Cancel`. The radios and the option row are one Tab segment (the radio row has `TabToSelected`, so Tab and S-Tab land on the current mode's radio); each input is its own stop; the Capitalize checkboxes are one segment; the buttons the last. The radio and option rows share four column widths (`massRenameColumnWidths`, the single source for the columns), so Up/Down, which go to the cell drawn nearest, keep the column. The dialog is as tall in every mode (`massRenameDialogHeight`), so External/Capitalize give the rows they do not use to the preview. Switching modes keeps focus on a widget both modes show, else moves it to Show only modified (`MassRenameClampFocusAfterModeChange`); re-entering the main screen focuses `massRenameHomeFocus(mode)` (the Find input, or Show only modified without inputs).
- **Apply** (M-a, `ApplyMassRenameKeepOpen`) runs the same validate-and-execute pipeline without closing: refreshes panels, re-selects the batch under its new paths, refreshes `MassRenameSources`, clears the fields and `MassRenameExternalNames` (re-arming the External gate), recomputes the preview and refocuses `massRenameHomeFocus(mode)`. It also sets `FileDialogState.MassRenameApplied`, so `CloseFileDialog` clears the active panel selection when the dialog later closes by any route. OK (`ExecuteMassRename`) clears the selection itself; both paths toast "Renamed N file(s)" at `MessageUrgencySuccess`.
- **Saved patterns**: `[dialog.mass_rename]` `file.mass-rename.load-pattern`, `file.mass-rename.save-pattern`, `file.mass-rename.history`, `file.mass-rename.delete-pattern`. `FileDialogState.MassRenamePhase` (`internal/ui/dialog/state_file_dialog.go`) selects the screen of the one dialog: `Main`, `SavePrompt` (stashes Find/Replace in `MassRenameSavedFields`), `LoadPicker`, `HistoryPicker`, `OverwritePicker`. The pickers share `MassRenamePatternPickerState`, `pickerView` and `Handler.handleMassRenamePickerKey` (over `Handler.handlePickerKey`); `dialog.MassRenamePickerPhase` is the single predicate for them and `currentMassRenamePickerState` picks the backing state (history vs load/overwrite). Pickers preselect the last loaded/saved pattern (`massRenamePatternName`). `file.mass-rename.save-pattern` on the save prompt opens the Overwrite picker (a second action on the same chord in that overlay would fail `keymap.Build` chord uniqueness): `overwriteMassRenamePattern` -> `ops.UpsertMassRenamePattern`, keeping name and description unless Description was typed. Patterns live in `patterns.toml` (`[mass_rename].file`, else `<config dir>/patterns.toml`, `internal/ops/mass_rename_patterns.go`); history is session-only (`maxMassRenameHistory`).

## Mkdir, duplicate, attributes, extract

- **Mkdir** (`file.mkdir`): prefill from the cursor (files drop the last extension; directories and bare dot-names keep the name). After Create the active panel highlights the new directory (`SelectVisibleEntryInViewport`, honors `scroll_mode`). `file.mkdir-open-in-other` sets `MkdirOpenInInactive`: the inactive panel enters the new directory. With selections the dialog adds Create / Create and copy / Create and move radios (`MkdirShowActions`, `MkdirAction`; M-r / M-y / M-m work while the name field is focused). With 2+ selections `file.mkdir.extract-common-name` (`[dialog.mkdir]`) prefills the longest common substring (`ui.ExtractLongestCommonName`). `executeMkdir` creates first, then queues `TypeCopy`/`TypeMove` via `Deps.Jobs`; copy/move variants clear selection, plain Create doesn't. Local mkdir is synchronous; remote runs on a worker and lands via generation-tagged `RemoteFileOpPayload` -> `ApplyRemoteFileOp` (so an SFTP password prompt can be delivered), taking copy/move sources from the listing snapshot (no Stat).
- **Duplicate** (`file.duplicate`): exactly one entry (file or directory); the destination is the exact copy target. The name prefills via `ops.SuggestDuplicateName`: the original name plus the first `.N` (N = 1, 2, ...) whose path is not in the panel listing (`ListingEntryAt`, no filesystem IO). Name field matches rename semantics (`file.rename.open-sanitize` / `file.rename.open-slugify`, **Focus after duplicate**, `rename_focus_after`) and queues a copy job via `ops.ValidateDuplicateSource`/`PlanDuplicate`; focus applies after the job completes and the entry exists.
- **chmod/chown/symlink/hardlink**: `PlanChown` trims both fields, rejects both-empty, and uses UID/GID `-1` for an omitted side. `executeChmod`/`executeChown` plan on the caller, then `startAttrOp` runs syscalls on a worker and completes via `RemoteFileOpAttr`. Symlink/hardlink use the plain file-dialog submit path. All four are blocked on non-local panels with `pathloc.Unavailable` (message names the panel scheme).
- **Extract** (`file.extract`, File menu `x`): destination defaults to the passive panel; enqueues `TypeExtract` (`Job.ExtractAsDirectory` -> `ExtractPlan.AsDirectory`); the worker runs `internal/archive` + `ops.ExecuteExtract` through `cmdrun.Run` (no shell). Tools are found with `exec.LookPath`; unsupported/tool-less items are skipped at confirm time with a toast (that wording is only for those skips). Existing or batch-colliding stream outputs stay in the plan and use `ExtractPlan.Conflict` (set by `jobbridge.TransferFunc` to the jobs overwrite blocker). Container tools get keep-existing flags (`unzip -n`, 7z `-aos`, rar `-o-`, tar `-k`). The "Extract as directory" checkbox (`FileDialogState.ExtractAsDirectory`, `FileExtractAsDir`, mnemonic E) is on at every open: `extractOne` then extracts each container archive into `dest/<archive.OutputBasename>` (`MkdirAll` on the worker; an existing directory is reused), snapshotting the real `dest` before creating it so the new subdirectory is reported dirty. Stream formats ignore it. The plan built at confirm (`PlanExtract`) only validates; the flag rides on `ExtractPlan.AsDirectory` into `EnqueueExtractJob` (also through the remote probe), and the worker re-plans in `jobbridge` and sets it from the job. Archive tools write local paths only, so the flag adds no remote handling beyond that of the plain extract. Encrypted archives (zip, jar, 7z, rar): when a tool run fails with `archive.PasswordFailure` (marker strings from unzip, 7z and unrar output), `extractOne` asks `ExtractPlan.Password` (`ops.ArchivePasswordFunc`; `jobbridge` sets it from the `archivePassword` argument of `TransferFunc`, which `internal/app` binds to `App.promptArchivePassword`: the worker blocks on the Archive password dialog, serialized with the sudo prompt and SFTP prompts by the SFTP prompt lock; a canceled job ctx unblocks it) and reruns with `archive.PasswordArgv` (unzip `-P`, visible in the process list while it runs; 7z and unrar read the password from stdin through `cmdrun.RunWithStdin`). A rejected password re-prompts with `retry` true; Cancel reports `ItemSkipped` with `ReasonNoPassword` and the next archive continues. `ExecuteExtract` keeps the last accepted password in a local variable and passes it to every later archive first; it is never stored on the job, logged or shown. A nil `Password` leaves the tool's failure as the item's error. SFTP on either side goes through `extractStaged` (`internal/ops/extract.go`): a remote archive is downloaded by `copyFileTransfer` into an `os.MkdirTemp` directory (`pc-extract-src-*`, name kept so the format still matches) and a remote destination gets a second one (`pc-extract-dst-*`) that `extractOne` extracts into (as-directory subdirectory and stream output included) before `ExecuteCopy` uploads its top-level entries with `ExtractPlan.Conflict` as the resolver, so existing remote files follow the jobs overwrite blocker. Both are removed by `defer` on every outcome; the scratch work runs under `fschange.WithoutSink` so only the real local destination reports changes. `ExtractItem.Path` and `ExtractPlan.Destination` are host paths or `sftp://` URIs, `ExtractPlan.Password` is asked with the item's original path, and `ExecuteExtract` re-parses both per item. `planExtract` (`PlanExtract`, and `PlanExtractForJob` which keeps existing stream outputs for the resolver) stats through `extractStat` (`os.Stat` locally, `statEntryFollow` otherwise: `fsbackend.StatFollow`, which uses the optional `fsbackend.StatFollower` the SFTP backend implements with `client.Stat`, so a symlink to an archive or to a destination directory counts as that target and a dangling link is the normal stat error; `Backend.Stat` itself keeps lstat semantics). `copyFileTransfer` and `destinationIsDir` use the followed stat too, so a downloaded symlinked archive has the target's size and mode and a copy into a symlinked remote directory works and never stats a remote path on the UI goroutine: `ExecuteExtract` uses the remote probe whenever the destination or any source is remote, and `EnqueueExtractJob` sets `DestIsDir` true without a Stat (the planner already verified the destination is a directory, local or remote). Per-file results of the upload are not reported as operations (one row per archive); the upload wraps `ExtractPlan.Conflict` to count the files the answer skipped, and `ExecuteExtract` reports the archive's done row with `ops.ReasonKeptExisting(n)` ("3 kept existing", the one wording, rendered by the Operations pane like any reason). Progress: `extractRun.meter` (`transferMeter`) counts the download's bytes (`copyFileTransfer`'s `onWritten`, throttled by `ExtractPlan.Throttle`, which `jobbridge` sets from the `[jobs]` worker progress settings via `tc.throttle`) and takes the upload's from `ExecuteCopy`'s progress callback (destination file path); both reach `ExtractPlan.OnTransfer(userFacingPath, cumulativeBytes)` (the remote archive for a download, the remote destination file for an upload, never a temporary path). `jobbridge` turns it into `EventProgress` with `DoneBytes` (the throughput chart and ETA; the extract job still has no `TotalBytes`, so no byte ratio is shown) and `CurrentPath`; the per-archive `ExtractProgress` events carry the same cumulative `DoneBytes` so it never moves backwards. A remote destination is probed on a worker (`RemoteFileOpPayload`); `drawMultiFieldDialog` paints `FileDialogState.Message` for skip warnings.
- **Delete dialog**: the spec is `AltOnly` (the Yes / No mnemonics need Alt); summary from `ui.PathsDeleteImpact`/`FormatDeleteImpactSummary` via the shared disk-usage engine (`ReconcileDeleteDialogScans`, `internal/apphandler/dialog/delete.go`, reusing a selection snapshot rather than `ops.ResolveSource` per reconcile). `OpenDeleteDialog` calls `diskusage.Engine.InvalidateRoots` so earlier operations can't show stale totals; totals always descend into other mounts regardless of `disk_usage_descend_into_mount_points`. Rows are `DeleteListEntry` names (fitted by `FitPathForWidth` at paint into the view's reserved list region), height capped at 80% of the terminal with `DeleteDialogMaxListRows`, with a list scrollbar on the right border when entries overflow (`ctx.ScrollbarStyle`); `DeleteLayoutMinWidth` is cached at open; updates repaint via `paintDeleteDialogOverlay`/`renderDeleteDialogUpdate` without a full `ui.Render`. Focused Yes uses `dialog.button.active_destructive`.

## Rsync

- **Action** (`file.rsync`, File menu `R`, leader `S`, no default chord): `Handler.OpenRsyncDialog` (`internal/apphandler/dialog/rsync.go`) resolves the sources like Copy (`ops.ResolveSource`: selection, else the cursor entry; `..` is dropped; `panel.GhostRefusal`; a `fileindex://` source is converted with `pathloc.Locals`) and refuses to open, with an error message, when `rsync` is not on PATH (`exec.LookPath`, replaceable in tests with `SetLookPathForTest`). Destination: the inactive panel's path (`DialogDestinationField`, the path-picker field Extract shares, directories only here, with the `[dialog.transfer]` active / inactive path chords of `dialog.FileDialogHasDestinationField` dialogs).
- **State**: `FileDialogType` `FileDialogRsync`. `Fields` are Destination, Exclude, Bandwidth limit (KiB/s) and Extra arguments (`dialog.RsyncField*`); `RsyncSources` (the parsed local `pathloc.Path`s, the one source list the preview and the job read) / `RsyncAllDirs` are fixed at open; `RsyncOptions` (an `rsync.Options`) holds only the mode and the checkboxes (`applyRsyncEvent`: radios `RsyncModeUpdate` / `RsyncModeMirror` / `RsyncModeMove`; the checkboxes Archive, Checksum, Only newer, Skip existing, Copy dir contents, Compress, Dry run are one table, `rsyncBoxColumns`, that drives the grid, the toggling and the per-option tooltips). `rsyncView` (`internal/ui/dialog/rsync_view.go`) is the `dlg` spec: the Mode label and radios (own row, one Tab segment), a blank row and the Destination input (focused on open) come first, then the two-column checkbox grid (one Tab segment), each input a segment of its own; Copy dir contents is `Disabled` unless `RsyncAllDirs`; OK is `Destructive` in Mirror mode. The title is "Rsync", or "Rsync N items" (`fileDialogOuterTitle`).
- **One build**: `Handler.buildRsyncRun` turns the dialog into an `rsync.Options` for both the preview and the job: the destination goes through `resolveDestination` (like Extract; a `fileindex://` destination is refused), `rsync.Resolve` translates the locations (below), Exclude is split with `strings.Fields` into one `--exclude=` each, the bandwidth limit must be a whole positive number, Extra arguments are split with `cmdrun.ParseCommandArgv` and go before the paths. `updateRsyncPreview` (run after every option event, text edit, picker result and destination chord via `fileDialogExtra`) stores `rsync.DisplayArgs(rsync.BuildArgv(options))` (`rsync.Display` is the same tokens joined by spaces) in `RsyncPreview`, which `rsyncView` wraps between arguments, or the problem in `RsyncError` (shown in place of the preview), and marks the panel the destination points at (the warning styles for Mirror). The preview leaves `Options.Report` off, so it lacks the progress flags the job adds.
- **OK** (`ExecuteRsync`): an option problem keeps the dialog open with a message. Otherwise the options are remembered (`Handler.rsyncLast`, session only: mode, checkboxes and the three text inputs, not the destination), the dialog closes, the active panel's selection clears and `jobs.Handler.AddRsyncJob(rsync.NewTask(options, onDryRun), sources, dest)` queues the job (`jobs.md`, Task jobs).
- **`internal/rsync`** has no UI dependencies. `BuildArgv(Options)` is the only argv builder: `-a` (without Archive, `-r`), `-c`, `-u`, `--ignore-existing`, `-z`, `-n`, `--delete` (Mirror) or `--remove-source-files` (Move; rsync leaves the emptied source directories), `--bwlimit=N`, `--exclude=...`, `-e <ssh>`, with `Report` the output flags (`--out-format=%n`, plus `--info=progress2 --no-inc-recursive` when `Progress2` and not a dry run; a dry run uses `--out-format=%i %n%L` to itemize), the extra arguments, the sources (a trailing slash on each with Copy dir contents) and the destination, always with a trailing slash so a single file is never renamed to the destination name. `progress2Supported` runs `rsync --version` once (on a worker) and turns `Progress2` on for rsync 3.1 and newer; an older rsync runs without it and reports file names only.
- **Remote**: `rsync.Resolve` passes local paths through and turns at most one SFTP side into `[user@]host:path` (`pathloc.SFTPEndpoint`), with `-e "ssh -o BatchMode=yes [-p port]"`: rsync runs its own ssh (honouring `~/.ssh/config`), cannot reuse the SFTP panel's session and has no terminal, so a host that needs a password or an unknown host key fails with rsync's ssh error (exit 255) instead of asking. Both sides remote (`errBothRemote`) and `fileindex://` locations are rejected with a message. A remote path with spaces is passed unescaped (rsync 3.2.4 and newer escapes it itself).
- **Run** (`rsync.NewTask`, lease `rsync.Lease`): `exec.CommandContext` with `cmdrun.DetachProcessGroup` (a new session, no controlling terminal) and `cmd.Cancel` replaced by SIGTERM to the process group (`cmdrun.SignalGroup`) followed by SIGKILL after `terminateGrace`; a canceled context ends the job canceled. Stdout is split on `\r` and `\n` (`splitLines`): a line `parseProgress` accepts (`1,234,567  45%  12.3MB/s  0:01:02 (xfr#12, to-chk=34/100)`; only the digits of the byte count are read, so any locale's separators work) gives `DoneBytes`, `TotalFiles` (the `to-chk` denominator) and `DoneFiles` (denominator minus remaining); every other line is a file name and becomes `CurrentPath`. `TotalBytes` is `progressLine.TotalBytes`: rsync truncates the percentage, so `bytes*100/(percent+1)` is a lower bound that never has to shrink (nothing below 1%), exact at 100%; on success the totals are completed. stderr is kept in a `cmdrun.CappedWriter` (`stderrCap` is the only limit on its lines). Before rsync starts, `checkDest` fails a run whose absolute (local) destination exists as a non-directory or has no existing parent (rsync creates only the last component and its dry run does not notice the missing parent); it is skipped for a remote destination and when Extra holds `--mkpath`. Every non-blank stderr line becomes a job warning (`warnStderr`, shown in the Messages pane), on exit 0 as well; exit 0 completes and any other code fails with only `exitMessage` as the error. A dry run reads the itemized lines (`itemizedName`), counts them as `DoneFiles` and, on success, calls `onDryRun(changes)` (nil when nothing would change). The handler posts `RsyncDryRunPayload`; `ApplyRsyncDryRun` (main goroutine) sets `Task.Results` ("N changes", or "No changes") whose `Show` opens the lines in the command output dialog (`CommandOutputDialog`), then toasts and syncs the jobs list.
- Not in the dialog (use Extra arguments): filter rule files, `--link-dest`, `--backup`, chmod/chown mapping, daemon targets, pause, per-file conflict prompts. No undo.

## Flatten

`file.flatten` (File menu `F`) needs a directories-only selection (mixed aborts with a toast before the dialog). Destination prefill follows `[operations].flatten_default_location`; options `flatten_recursive`, `flatten_remove_empty_dirs`. Destination footer: Bookmarks / History / Pinned / destination-panel shortcuts (see Path picker below and [navigation.md](navigation.md)). On OK, `confirmFlatten` validates synchronously (`ops.ValidateFlattenTarget`: roots non-empty, destination not strictly inside a root; the destination probe always goes through `RemoteFileOpPayload`) and enqueues `TypeFlatten` with nested roots pruned to minimal ones; the dialog walks nothing. The dialog is `FlattenView` (a `dlg.Spec`, see [dialogs.md](dialogs.md)): destination input, Recursive / Remove empty directories checkboxes, OK / Cancel; `Handler.HandleFlattenDialogKey` runs the completion dropdown and destination shortcuts first, then `dlg.HandleKey`, then the field editor, and `DrawFlattenDialog` paints the completion dropdown from the destination input's placed rect.

`ops.ExecuteFlatten` is a single streaming pass moving each entry through `moveAndCount` to `dest/<name>` (recursive descends; non-recursive moves immediate children, directories whole). Rules:
- Conflicts use the normal resolver; a skipped file keeps its directory.
- Non-recursive flatten expands same-name nesting (`aaa/aaa`) by processing the child's children.
- Files whose final path equals a flatten root are deferred to the end, parked as `<name>.flatten` (`.1.flatten`, ...), emptied directories removed, then renamed; if the final path still exists the job fails naming it.
- Remove-empty-dirs removes each directory right after its children when empty, roots included.
- No total is announced (jobs view shows `?`); `DoneFiles` counts moved items.

## Filesystem change reports

Every local primitive reports what it did through `ctx`'s `fschange.Sink` (ADR 0023; helpers `report*` in `internal/ops/fsreport.go`, the only place remote paths are dropped). Jobs get the sink from `jobbridge.TransferFunc`. Dialog operations get it from `Handler.fsCtx`, which `elevatedCtx` builds on, so async and elevated retries report too. Each report follows the step's success:

- **Renamed**: `RenameFastPath` (move renames, merge children, undo move-back), `ExecuteRename`, flatten's deferred park and final renames, and `ExecuteMassRename(ctx, rows)` as one batch of net source -> target renames (never the temp hops).
- **Removed**: `ExecuteDeletePaths` per source, `removePathRecursive` (delete-source answers, a move fallback's sources, staged overwrites), `removeDirIfEmpty` (merge sources, flatten, undo, `RemoveEmptyDirsUnder`), `undoRemoveCreated` files, `removePartialTransferDest`, and a failed stream extract's output.
- **Created**: `Options.noteCreated` (one `Lstat` shared with the undo journal) for copied files, symlinks and directories; `ensureParentDirs`, a copy's created destination directory, `ExecuteMkdir`, `ExecuteSymlink`, `ExecuteHardlink`, and stream extract output.
- **Dirty**: a delete source that failed, was cancelled or was skipped after a permission error; a failed local `CopyFile` (it truncates in place); and, for archive-tool extracts, each top-level entry of the destination that is new or whose mtime, size or kind changed (`snapshotTopLevel` before and after `extractOne`). A member added only to an existing nested directory leaves its top-level directory's mtime unchanged, so it is missed until a rescan; container tools run with keep-existing flags, so nothing is overwritten in place.

## Overwrite and directory mismatches

A conflict where exactly one side is a directory (real, or a symlink to one), or a directory meets a symlink to a directory, can only be skipped, renamed or canceled; nothing is merged through a symlink. `ops.FileConflictFacts.OverwriteUnsafe()` (`SourceTarget`/`DestTarget`, filled by `StatFileConflictFacts` and `statConflictFacts`) decides it, and `resolveConflict` converts any overwrite or delete-source on a mismatch into skip. The copy plan's directory items (`copyDirItem`) hit the same path: skipping drops the subtree (`copyRunState.skippedDirs`), renaming re-roots it (`renamedDirs`). Dialog details and remembered-decision handling are in [jobs.md](jobs.md); rationale in ADR 0011 and 0019.

## Copy/move destination dialog

- Shared state and renderer: `dialog.TransferDialogState` / `TransferView` / `DrawTransferDialog` (a `dlg.Spec`, see [dialogs.md](dialogs.md)). `file.move` always opens the destination dialog (even with one shared path and no selection); same-directory rename stays on `file.rename`. Destination is a path-picker `FileDialogField` prefilled with the passive panel path plus a trailing separator.
- Copy-only checkboxes: preserve permissions, preserve timestamps, dereference symlinks (M-r / M-t / M-d mnemonics of the widget spec); preserve toggles are stored on `jobs.Job` at enqueue. Dereference is greyed out (focusable, inert) when source or destination is SFTP (`TransferDialogState.DereferenceUnsupported()`); semantics in [jobs.md](jobs.md).
- Buttons in both phases (destination and self-copy rename): OK, **Advanced** (M-a), Cancel. Advanced sets `TransferDialogState.Advanced` (`StartAdvanced`) and swaps the spec for the Conflict rules screen: `conflictRuleGroups` (shared with `conflictRulesView`, which adds Apply-to-all) plus the `TransferStartPaused` (**Add paused**, enqueues `StatusPaused`) and, for a move, `TransferRemoveEmpty` (**Remove empty directories**) checkboxes. `TransferDialogState.Rules` is a `ConflictDialogState` reused for `ApplyRule` / `ToggleVerify` / choice greying, seeded once with a synthetic conflict blocker so Delete source shows only for a move. `Screen` returns the spec with its focus pointer (`Focus`, or `AdvFocus` on the advanced screen) for key, click and render paths; OK confirms, Cancel (and Esc) returns to the main screen keeping the choices. `applyTransferAdvanced` puts the rules (only when they differ from the default, `RulesChanged`) and the remove-empty choice on `jobs.TransferPreserve`.
- Destination-row footer: Bookmarks, History, Pinned, and `ui.destination-active` / `ui.destination-inactive` (labelled "Active path" and "Inactive path"). The same action pair is bound in `[dialog.transfer]` and `[dialog.flatten]`.
- **Destination resolution**: Copy/Move, Flatten and Extract resolve the typed destination once at confirm via `Handler.resolveDestination` -> `pathpick.ResolveDestination` (the same `ResolveQuery` the dialogs validate with: `~` against `Model.UserHomeDir`, relative against the active panel; `sftp://` as given), then pass `destLoc.String()` downstream so nothing re-parses the raw text against the process cwd.
- **Destination target highlight**: while the destination field is open and its text resolves to a panel's cwd, that panel's frame/title use `panel.target.frame` / `panel.target.title` for Copy, or `panel.target.warning.frame` / `panel.target.warning.title` for Move and Flatten (`PanelContext.IsTransferTarget` + `TransferTargetWarning` in `drawPanel`, fed by `Model.DestinationTargetWarning`). Computed on the same debounced tick as `DestPathInvalid` (`updateDestinationTargetPanels` via `pathpick.ResolveQuery`, `[ui].path_picker_validate_delay_ms`); both panels light up if both match. Reset on close and when a self-copy rename starts. Local paths only. Extract uses the Copy styles (`updateExtractTargetPanels`: on open, on every destination edit or completion accept, and for the active/inactive-path shortcuts; not debounced since it does no IO). Duplicate (`file.duplicate`) marks the active panel's cwd (and the other panel if it shows the same directory) as a Copy target when its dialog opens; `CloseFileDialog` clears it for both.
- **Focus transferred entry** (`[operations].focus_other_panel_after_transfer`): `AddTransferJob` arms the shared `pendingPanelFocus` (also used by duplicate focus-after; retried by `RefreshBothPanels`/`ReconcilePendingPanelFocus`) when the destination equals the inactive panel's cwd, with the top-level dest names and a snapshot of that panel's cursor path. After the terminal refresh it selects the first candidate via `SelectVisibleEntryInViewport` only if the panel is still there and the cursor hasn't moved.
- **Multi-location preview**: when the selection spans more than one parent, `App.openTransferDialog` (the single copy/move funnel) fills `TransferDialogState.CommonRoot`/`.Entries` and the same dialog gains a **Source:** header and **Result** preview (`MultiLocation()`; the Result list shows up to `TransferListMaxRows` rows in a dialog of at most `listDialogMaxHeight`, read back from the fitted `TransferView`). It triggers regardless of the panel's current path. Width is computed from un-flattened labels so toggling **Flatten into destination** (M-i, last content row) never resizes. `App.multiDirSelectionCommonRoot` -> `panel.State.SelectedCommonRoot` (`pathloc.CommonAncestor`). Mixed-scheme or single-directory selections skip it. Sources are re-resolved from `SelectedPaths` at confirm. The span also drives the selected-strip icon ([panels.md](panels.md)).
- **Structure preservation**: destination names are batch-relative to the sources' deepest common parent (`ops.TransferNameRoot`/`TransferDestName`, `ResolveDestinationNamed`): `dir_a/f1`, `dir_a/f2`, `dir_b` copy to `dest/dir_a/f1`, ... unless Flatten-into-destination is checked. Move fast path creates missing parents (`ensureParentDirs`) for nested batch-relative names and for a file-target destination (a single source moved onto a new file path: an exact-destination job, see [jobs.md](jobs.md)). `ops.SelfTargetCount(sources, destDir, flatDestNames)` stats `destDir` once (not per source); the flatten dialog uses it too. One source of truth for flat naming: `Job.FlatDestNames()` (`TypeFlatten || FlattenIntoDest`) feeds `ops.Options`/`PlanBuildOptions`/`ScanWalkHooks.FlatDestNames`; `TransferPreserve.FlattenIntoDest` carries the checkbox through `AddTransferJob`. Local destinations are probed on the UI goroutine at confirm; remote ones on a worker (`RemoteFileOpPayload`) so a password prompt can't deadlock confirm; `AddTransferJob` never Stats a remote destination. Tests: `internal/ops/transfer_structure_test.go`.
- **Self-copy/move**: if the resolved destination equals the source (`ops.ResolvedSameAsSource`) a single transfer switches to a **New name** step (`TransferPhaseSelfCopyRename`); reusing the original name errors. Multi-source self-overwrite is rejected with a warning. Copying into a strict subdirectory of a source is rejected at plan time (`ops.DestinationUnderSource` in `BuildPlanCtx`).
- **Dangling directories** (`[operations].remove_dangling_directories`): browser move/delete jobs get `Job.PromptDanglingDirs` at enqueue (`AddTransferJob`/`EnqueueDeleteJob` apply the config gate; callers pass `promptDangling`). On `EventCompleted`, `stashDanglingSourcesForCompletedJob` stashes `Sources` with no I/O; `ApplyRefreshes` drains it and `ops.DanglingDirsAfter` (`internal/ops/flatten.go`) climbs from each source's parent while entries are emptied directories, returning only the topmost of each chain. `Host.PromptDanglingDirDelete` either toasts "N empty directories left behind" (another modal open) or opens the delete dialog with `DeleteDanglingDirs` set, **Yes** default (already-empty dirs are low risk). `ExecuteDelete` checks `DeleteDanglingDirs` before the `ViewMode` branches and queues `EnqueueEmptyDirsDeleteJob` (no loop): `Job.DeleteEmptyDirsOnly` runs `ops.ExecuteRemoveEmptyDirs`, which removes with rmdir only (its elevation argv too), so a file that arrived since the check is safe and its directory stays (`ItemSkipped`, `ReasonNotEmpty`). `updateJobMessage` replaces "Job completed" with a warning naming how many were kept (`Ops.Stats().Skipped`). The no-prompt `RemoveDanglingDirs` drain uses the same job. `removeDirIfEmpty` goes through `fsbackend.DirRemover`, so no empty-directory cleanup can unlink a file. Dedup deletes pass `promptDangling=false`: they have their own empty-dirs confirm (`openDedupEmptyDirsConfirm` via `Deps.Dedup`, see [views.md](views.md)). A move enqueued with `TransferPreserve.RemoveEmptyDirs` gets `Job.RemoveDanglingDirs` instead (`PromptDanglingDirs` false): `stashDanglingSourcesForCompletedJob` stashes it into `pendingRemoveDanglingSources` and `promptDanglingDirsIfAny` queues the found directories with `EnqueueDeleteJob(paths, false, false)`, no prompt. Test: `internal/ops/dangling_test.go`.

## Path picker validation and completion

- Path-picker hosts: bookmarks quick-cd, plus Bookmarks / History / Pinned / All apply-to-field pickers for transfer, flatten and any `PathPicker` file-dialog field (see [navigation.md](navigation.md)).
- History lists drop paths that no longer exist; bookmark rows show a missing indicator. Ghost completion is not cached: `pathpick.SuggestAtCursor` runs `os.ReadDir` on the resolved parent, and open fields re-sync after panel refresh and on each debounced validate tick. `EnsurePathInputScroll` keeps the caret visible after Tab/End.
- **Validation**: path-shaped text (absolute, contains a separator, leading `~` or `.`) is `Lstat`ed after an idle debounce (`[ui].path_picker_validate_delay_ms`); each keystroke restarts it, and `pathPickerValidateGen` / `transferDestValidateGen` (`internal/app`) discard stale `time.AfterFunc` callbacks. Plain fuzzy text skips `Lstat`. Missing paths use `dialog.input.active.error` / `dialog.input.inactive.error`.
- **Completion**: with the caret at end-of-line and path-shaped text, the ghost suffix is painted in `dialog.input.*.placeholder` (`QueryCompletionSuffix`/`DrawScrollingDialogInput`; destination field via `CompletionSuffix`/`drawInputField`). Tab accepts it (appending `/` for directories) instead of moving focus; with no suffix, Tab moves per the form. The destination field shares the same shape and debounce rules (`DestPathInvalid`, `DestPathCheckPending`).
- **Create directory row**: when `pathpick.Suggest` has nothing, `syncPathCompletion` calls `pathpick.MissingDir` (caret at the end, value ends with a separator, path-shaped, not a URI, no relative path on a URI panel, resolved path `Lstat`s as not-exist). If it finds one, `PathCompletion.SetCreate` offers the single `Candidate{Create: true}` row (`PathCompletionCreateDirLabel`, `CreatePath` = host path). The row auto-opens although the segment is empty, and a same-value resync keeps Esc's close. `HandlePathCompletionKey` returns a `CompletionOutcome` (`CompletionNone` / `CompletionAccepted` / `CompletionCreateDir`); Enter on the row gives `CompletionCreateDir` and leaves the value alone; Tab closes the row and is not handled (it keeps moving focus, so typing a path and tabbing away never creates anything, and the row is not left painted over the next widget). Both callers (`tryPathFieldCompletionKey`, `HandlePathPickerKey`) then run `Handler.createCompletionDir`: synchronous `ops.ExecuteMkdir` with `MkdirPlan.Parents` (`localfs.MkdirAll`, elevation argv `mkdir -p`, `Created` reported for the topmost new directory via `fsCtx`, no elevation prompt), an info toast or a `Create directory` error. After that they follow the accept path: re-arm validation, resync completion.
